# Replace both row tables with one-file-per-row storage under `docs/work/{open,closed}/OW-N.md`. Decided by the owner on 2026-08-17

`docs/TRACKING.md`, `docs/WORKSTREAMS.md`, `docs/CLOSED.md`, `AGENTS.md`, `.claude/skills/author/SKILL.md`, `.claude/skills/execute/SKILL.md`, and four files phase 3 would otherwise leave pointing at nothing: `docs/DESIGN.md`, `docs/MANUAL_TESTING.md`, `docs/HANDOFF.md`, `README.md`

this was a `question` until then. The design, the evidence, and the five
questions that settled with it are in `docs/TRACKING.md`; read it and do not
restate it. What forced the decision, in one line: authoring now happens on a
work laptop and implementation on a home server, so one clone only adds rows and
the other only removes them, and it still conflicts on essentially every close
because both write the table's tail — under one file per row those are disjoint
paths and the merge is clean however long the clones diverge. **Implement the
doc's "Staying greppable" constraints literally:** a one-line `# `-prefixed
headline that never wraps, one-line flat frontmatter scalars, `##` for body
subheadings, and any list command piped through `sort -V` rather than trusting
the searcher's order (every searcher here walks files in parallel; ripgrep gave
five orders in five runs). All three were measured against a prototype and they
outlive OW-59 — `ow list` needs the same sort, and the wrapping and scalar rules
are what any parser depends on. **The headline is the row's existing lead claim,
not a truncation of its first cell** — load-bearing rather than cosmetic,
because `rg -N '^# '` is now how both modes survey the list (`TRACKING.md`
finding 5) and a vague headline makes a row invisible. Measured to be
near-mechanical; the rule and the count are under "Migrating". **Both files
migrate**, every open row and every closed one — 42 and 27 as of 2026-08-17, but
**take the counts yourself at the start of phase 1 and carry those.** Every
count written into this row or into `TRACKING.md` was true when written and
drifts with each row authored on the laptop; this row already went stale by one
within hours of being written. A done-when checked against a literal here is a
done-when that fails for the wrong reason, and the tempting repair is to edit
the number rather than find the missing row. **Run it in the three phases
`docs/TRACKING.md` sets out under "Migrating"** — generate alongside and verify
mechanically, rewrite the process docs, then delete — because a migration cannot
be verified once its source is gone, and because each phase ends at a commit
leaving the repo coherent. That is deliberate room to breathe: **this row does
not have to land in one session.** Stop at a phase boundary and name it; do not
stop mid-phase. **Phase 1 is done when** every row of both tables has a file
under `docs/work/`, the equivalence check in `TRACKING.md` passes over all of
them, and one commit carries the tally — *not* when the Done-when at the end of
this row is met, which is phase 3's criterion and would have you run all three
phases in one session. **One phase per session, and phase 1 ends yours** — hand
back after it rather than carrying on. The reason is no longer context volume:
under a script the converting session never holds sixty-nine row bodies at all,
so the earlier version of this clause argued from a cost the fan-out had and
this does not. What survives is the stakes and the reader. Phase 2 rewrites
`AGENTS.md` and both skills — the prose loaded into every future session —
against storage that phase 1 has just invented, and those edits want a session
that reads the new storage cold rather than the one that spent its context
arguing its own transform correct. **How a later session knows where it is:**
`git log --oneline --grep='^docs: OW-54 phase'`, which means **each phase
commit's subject must begin `docs: OW-54 phase N`** — and the `^docs: ` anchor
is load-bearing, not tidiness. A bare `--grep=OW-54` matches every authoring
commit for this row, twenty of them by 2026-08-17. Worse, the unanchored
`--grep='OW-54 phase'` searches the whole commit message rather than the
subject, so it matches `e82a9a9` — the very commit that introduced this token,
whose body quotes it — and a fresh session running that form today gets exactly
one hit, concludes the phase-1 commit exists, and starts phase 2 against a
`docs/work/` that was never created. Both forms were run on 2026-08-17; the
anchored one returns nothing, which is the correct answer before phase 1. The
phase-1 commit is the one carrying the converted-row tally, so its presence
means phase 1 is done and you are starting phase 2; phase 2's commit means you
are starting phase 3. There is no state to find anywhere else, and `docs/work/`
existing while the tables also exist is exactly what phase 1 leaves behind
rather than a half-finished phase. Resume by invoking `/execute OW-54` again —
the row stays open across all three, and closes only after phase 3, as
`docs/work/closed/OW-54.md`. **Phase 1 is one transform script plus one
read-only spot-check agent, and is explicitly not a subagent fan-out** — the
owner reversed the fan-out on 2026-08-17 once the conversion spec became
deterministic, measured across all 69 rows: two mechanical rules extract every
headline with nothing left over. `TRACKING.md` carries that measurement, the
reasoning, and the one dispatch it does permit, which is pre-authorised so you
need not ask for it. Do not ask to reintroduce the fan-out. That section also
carries the strikethrough and `git mv` details for closed rows, the measurement
showing headline extraction is near-mechanical, and which of the two files
survives. **No index file is committed** — that is a settled finding, not a
