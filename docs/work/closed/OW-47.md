# Autoscroll degrades over a long conversation until it stops entirely — cause unknown, reproduce before fixing.

Reported live 2026-08-14, with a clear progression *within one conversation*:
early turns behave exactly to the OW-27 spec (the submitted prompt rises until
it reaches the top of the pane, where autoscroll stops); later turns stop
earlier and earlier with the prompt still mid-pane; eventually submitting only
appends the message at the bottom of the panel and nothing scrolls at all while
the answer streams. **Reloading does not help; starting a new conversation
does**, in the same page session. Autoscroll arms on submit (`armFollow`), and
stops on exactly the three conditions of the agreed spec (OW-27): a manual
scroll, the prompt reaching the pane top, or the turn ending. The symptom means
one of the three fires early — **this row is to find out which, not to pick
one.** Three candidates, none confirmed: (a) *phantom manual scroll* from two
programmatic scrolls racing the boolean `suppressScrollHandling`; (b) *premature
turn-end* from an `isStreaming` false mid-stream; (c) *anchor lost*, `reconcile`
silently scrolling nothing when `querySelector` misses. Reproduction vehicle:
OW-27's close note records live-browser verification via synthetic SSE, but no
such harness is in the repo — rebuild it, and commit it this time. Done when:
the cause is identified from logged evidence in a real browser, recorded in
`MANUAL_TESTING.md`; a failing-first test pins it; and a long conversation
autoscrolls on every turn the way its first few do.

**Fixed** in `20470d3`, with a one-declaration change: `overflow-anchor: none`
on `.conversation` (`src/client/app.css`). **The cause was none of the three
candidates.** It is **CSS scroll anchoring** — the browser repositioning
`scrollTop` itself to hold a visual anchor steady as content reflows above the
viewport, under-compensating (~10px per adjustment, instrumented) as it does.
That fires a `scroll` event the application never performed, and
`handleConversationScroll` cannot distinguish it from a reader grabbing the
scrollbar, so it clears the anchor and follow disengages mid-turn. Candidate (a)
was the right *shape* — a phantom scroll read as manual — but the wrong source:
not two programmatic scrolls racing one boolean, but the browser scrolling on
its own. Two anchoring mechanisms on one scroller fight; follow mode already
does this job against a message it picked, so the browser is told to stop doing
it too. **A guard against the boolean race was written, measured to change no
outcome, and reverted** rather than landed speculatively — that race remains
real but unproven, filed as OW-48. Evidence in `MANUAL_TESTING.md` ("Observed
follow-mode decay in a real browser"): headless Chromium 151, all 10 turns of a
40-turn-deep conversation lock flush at the pane top (≤2px) with the fix; with
it reverted the first measured turn strands **51px** down. Fail-first
re-confirmed independently in review by `sed`-ing the declaration out and
re-running. **Reproducing it requires a turn shape that *shrinks* mid-turn** —
`Thinking.svelte` holds its `<details>` open only while it is the streaming
block, so a landing `toolCall` collapses it and the transcript gets shorter;
text-only turns were driven to 200 seeded turns and never reproduced it. Any
future follow-mode harness needs a contracting turn, not just a growing one.
Lands the repo's **first browser vehicle** (`e2e/`, Playwright, `bun run
test:browser`): the real `App.svelte` and real `controller.ts` against a
synthetic `AgentpaneApi` port, no backend and no subprocess. jsdom has no
layout, no scroll anchoring and no real scroll-event timing, so it could not
have discovered this and cannot pin it. Deliberately one defect's harness,
**not** the E2E suite OW-24 still tracks; not wired into `bun run check` because
it needs a browser (OW-49). `bun run check` green at 612 tests, unchanged — the
pin lives in the browser vehicle. The executing agent was terminated mid-task by
a spend limit having reverted the speculative guard; review verified the fix,
the fail-first, and `bun run check` on `main`, and wrote the `MANUAL_TESTING.md`
and `AGENTS.md` entries it had not reached.
