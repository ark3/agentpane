# Whether agentpane should set `approvalPolicy` on its threads, and whether doing so (or the sandbox policy) suppresses Codex's approval `ServerRequest`s.

**Live Codex run required.** Codex is installed on the home server, so this needs no work-laptop trip; only Pi is confined there.

Codex approvals (D2a)

Two coupled parts. (a) *Does anything already suppress them?* app-server may
still raise exec/patch approval `ServerRequest`s (the `tool-edit` fixture has a
live `item/fileChange/requestApproval`) even on a `danger-full-access` thread
(OW-37); unverified. The old framing — that sbox's injected `--sandbox
danger-full-access` governs this — was wrong: that CLI flag is a no-op for
`app-server` (OW-37), so the effective levers are both per-`thread/start`. (b)
*Should we set `approvalPolicy:"never"`?* `approvalPolicy` is an
`AskForApproval` field (`resources/codex-protocol/v2/AskForApproval.ts`,
includes `"never"`) on both `ThreadStartParams` and `TurnStartParams`, sent by
the adapter at the same sites as OW-37's sandbox field
(the `thread/start` and `thread/resume` calls in `start()`, and the `turn/start`
request, all in `src/server/adapters/codex/adapter.ts`);
agentpane sends none today, so the thread defaults to `"on-request"` (observed
in the OW-37 probe). Given the sandbox flag is a no-op for app-server, the safe
prior is that the top-level `--ask-for-approval`/`--approval-mode` CLI flag is
too, and only the per-thread `approvalPolicy` bites — but that is the thing to
verify, not assume. The decision hinges on D2a, and this card's original reading of
that was wrong: it said agentpane forwards approval requests to the browser, so
`"never"` trades a dialog for no dialog. It does not. OW-bijera records that the
client's entire response to a pending request is one `<p class="warning">Unsupported
agent request pending.</p>`, after which the turn hangs until the session is
killed. The real trade is no dialog against a hung turn, which is what the
amendment below decides on. Verify at the source before
deciding: a probe that starts a thread with and without
`approvalPolicy:"never"`, drives a turn that edits a file, and records whether a
`ServerRequest` reaches the wire (extend `resources/probes/codex_turn_probe.py`,
or the sandbox probe from the OW-37 investigation). Settling this leaves this
list and becomes a D-decision in `DESIGN.md`.

## Amended and decided 2026-09-11

The owner decided that agentpane sets `approvalPolicy: "never"`.
The intent is to avoid permission prompts, not to route them into agentpane's UI, and that intent is what settles part (b) without waiting on the run.
sbox was considered as the site and rejected: it injects before the subcommand (`codex --sandbox danger-full-access app-server`), so a CLI approval flag would be the same no-op the sandbox flag already is, and the `-c approval_policy=never` route app-server does accept would put a hidden global outside the repo, contradicting an adapter option that sets the sibling policy and invisible to `bun run check`.
The site is `CodexAdapterOptions`, beside `sandbox`, which the adapter already applies at thread creation.

Part (a) is still a live-run question, and so are two others that the run should answer in the same sitting.

`ThreadForkParams` and `ThreadResumeParams` accept `approvalPolicy` too, not only `ThreadStartParams` and `TurnStartParams` as the body above says.
So the change carries both policies on all three thread-creation paths rather than on start and resume alone; OW-laliku holds the evidence question about whether a fork inherits, and is the reason this is not assumed either way.

`item/toolRequestUserInput` is not an approval -- it is a tool asking the user a question -- and there is no obvious reason `"never"` would suppress it.
Whether it can still arrive is what decides whether OW-bijera is moot or real, so provoke it deliberately rather than reporting that it was not seen.

## Close note

agentpane sets `approvalPolicy: "never"` on its Codex threads, and the three live questions are answered — two of them, and the third recorded as unreachable rather than dressed up as an answer.

The decision is `docs/DESIGN.md` D7a, "Codex approval policy: `never`, set by the adapter", placed beside D7 following the D2a precedent for a decision that sits topically beside an earlier one. It says the site is `CodexAdapterOptions.approvalPolicy` and why not sbox (injects before the subcommand, so a CLI approval flag is the same no-op the sandbox flag is for `app-server`) and why not `~/.codex/config.toml` (a hidden global outside the repo, invisible to `bun run check`).

The adapter sends both `sandbox` and `approvalPolicy` on all three thread-creation paths — the `thread/start` and `thread/resume` calls in `start()` and the `thread/fork` call in `fork()`. `turn/start` is not a thread-creation path and was left alone. Three assertions in `src/server/adapters/codex/adapter.test.ts` cover the three request shapes; all three were watched fail against the unchanged adapter and pass after. Nothing had previously asserted `fork()`'s params at all.

The run: `resources/probes/approval_policy_probe.py`, new, eight cells, 2026-09-11 on the home server against `codex-cli 0.154.0` with `gpt-5.6-luna`. Neither existing probe could host it — `codex_turn_probe.py` has no request bookkeeping, and `fork_probe.py` answers every server request uniformly and keeps no separate record of them. Written up in `docs/MANUAL_TESTING.md`, "Observed Codex approval policy, and what a fork carries (OW-18)".

What it showed, in order of how much it changed:

**A fork inherits `approvalPolicy` but not `sandbox`.** Forking a `dangerFullAccess` parent with only `threadId` and `cwd` returns a thread reporting `workspaceWrite` — app-server's own default, licensed as such because the copied config sets no sandbox key. A second fork cell from a parent started with `"never"` came back `"never"`, which is what distinguishes inheritance from fallback. So carrying `sandbox` on `thread/fork` is not symmetry, it repairs a silent downgrade the fork was already taking. This is what OW-laliku was asking.

**`approvalPolicy: "never"` suppresses the approval request where one would otherwise arise, but nothing arises under agentpane's sandbox.** The `read-only` pair is the control: the same edit prompt raised one `item/fileChange/requestApproval` under `on-request` and none under `"never"`. On `danger-full-access` no approval arrived under either policy — the sandbox grants the write and `on-request` has nothing to ask about, which is an absence of occasion and not a suppression result. So the policy was not shown to be doing work today; its value is that it stays correct if the sandbox ever narrows. `item/fileChange/requestApproval` is the only approval kind any cell provoked.

**`item/tool/requestUserInput` could not be provoked**, on two deliberate attempts, one of them naming the tool and declaring `experimentalApi: true` in `initialize`. Both drew "the user-input tool is unavailable in the current mode" with no tool call of any kind. Recorded as unsettled and explicitly not as evidence either way.

That third result is why OW-18's conditional over OW-bijera fired into neither branch. Both branches are discharged in OW-bijera itself, which now records that the approval kinds are doubly out of reach under agentpane's configuration and that nobody can stage its live run; `OW-zogogo` was filed to carry the remaining question — whether any `ServerRequest` kind can reach agentpane at all. OW-bovase now names D7a as the durable citation its decline note was waiting for.
