# DESIGN's Codex mapping table is wrong in three ways: it reads as exhaustive, its content-block row describes the legacy type, and it lists a capture that now exists as missing.

**Decided by the owner on 2026-08-19: say the table is non-exhaustive rather
than grow it.** The counts, taken 2026-08-19: `ThreadItem` carries 18 variants,
`mapItem` maps 12, `SILENT_ITEM_TYPES` deliberately swallows 5, and DESIGN's
table has 10 rows. The table was never a registry, and making it one would
contradict the design it documents -- `mapping.ts:294-299` returns
`kind: "none"` for an unrecognised type precisely so a routine `codex` upgrade
cannot take a session down, and a table claiming to be complete would be stale
at every such upgrade. The code is the better registry: one switch plus one
named set, each carrying its reasoning.

## The three corrections

**1. The item table (`:630-641`) is incomplete and should say so**, with a
pointer to `src/server/adapters/codex/mapping.ts` as the registry. The arms
beyond it are `imageGeneration` and `imageView`, neither silent, both producing
output.

**2. The content-block line (`:642-643`) is factually wrong**, and
"non-exhaustive" does not cure it. DESIGN says `input_text`/`output_text` ->
`TextContent` and `input_image` -> `ImageContent`; those belong to
`ContentItem`, the **legacy** type. v2's `userMessage` carries `UserInput`,
whose variants are `text`/`image`/`localImage`/`audio`/`localAudio`/`skill`/
`mention`. `mapping.ts:131-137` already records this, including why
`localImage` and `localAudio` degrade to a text reference -- the reducer is
pure and cannot read the path. DESIGN should agree with it.

**3. The fixture-coverage paragraph (`:651-654`) still lists
`contextCompaction` among the rows with "no capture yet".** It has one:
`resources/fixtures/codex/compact.jsonl`, committed by OW-72. This correction
arrived here from OW-6's close rather than being filed separately, because it
is the same table wrong in the same way. Check the rest of that sentence while
editing it -- `plan` genuinely still has no capture (OW-19), so the paragraph
is right about some of its list and wrong about one entry.
