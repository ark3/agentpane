# Hitting Compact gives zero feedback until it completes — no status, no disabled button, for the many seconds a compaction runs.

Observed on a live Pi run (this session): clicking **Compact** posts to the
backend and then shows nothing at all until the summary appears — no status
line, the button does not disable, and a compaction is not fast (the OW-72
capture's compaction turn alone ran ~90s). The click feels dead. Cross-backend,
not Pi-specific: Codex runs compaction as its own turn and the client has the
same blind interval.

## Why it happens — two feedback channels, compaction touches neither

- **`view.busy`** drives the status line (`App.svelte:132`, e.g. "Sending
  prompt…", "Aborting turn…"). `submit()` and `abort()` set it before their
  request and clear it in `finally`; **`compact()` never sets `busy`**
  (`controller.ts:314`), so the line stays `idle`.
- **`isStreaming`** drives the Abort button and the streaming dot. On Pi it
  flips on `agent_start`/`agent_settled`; a manual compaction emits
  `compaction_start`/`compaction_end` instead, and the reducer deliberately
  gives `compaction_start` no effect on `isStreaming` (`reducer.ts:147`). So
  that indicator never lights either.

## The fix — the `busy` channel, mirroring abort()

Route the signal through `busy`, not through any backend event: it brackets the
request, so it works identically for both backends, and `compaction_start` is
Pi-only and does not reach the client view model anyway. Add a `"compacting"`
member to the `busy` union (`controller.ts:21`), publish `{ busy: "compacting",
error: null }` before the `await api.compact(selected)` and clear it in a
`finally` guarded by `view.busy === "compacting"` — the exact shape `abort()`
already uses (`controller.ts:305`). Add the matching `statusText` case
(`App.svelte:132`), e.g. "Compacting context…".

Then **disable the Compact entry while compacting** so a second one cannot fire
mid-run — bind its `disabled` to `view.busy === "compacting"` (on top of the
existing nothing-selected guard) at the tools-menu button (`App.svelte:752`).

Incidental: the exact status wording, whether other composer controls also
disable during compaction. Load-bearing: `busy` reads a distinct compacting
state across the whole request, the status line shows it, and Compact is not
re-clickable while it runs.

## Done when

A `controller.test.ts` test holds `api.compact` open with `deferred<void>()`
(the pattern the mid-submit `busy` tests already use, ~314), asserts
`getView().busy === "compacting"` after the call and before resolving, and
`=== "idle"` after — failing against today's `compact()` (which never leaves
`idle`) and passing after. `bun run check` green.

**Fixed** in eb78ef1: `compact()` now brackets its request through the `busy`
channel exactly as `abort()` does — `publish({ busy: "compacting", error: null })`
before `api.compact`, cleared in a `finally` guarded by `!disposed &&
view.busy === "compacting"` so a later state is not stomped. The status line
gains "Compacting context…" and the tools-menu Compact entry disables on top of
its nothing-selected guard.

Watched red first: the new `controller.test.ts` test holds `api.compact` open
with `deferred<void>()` and failed `expected 'idle' to be 'compacting'` against
the old `compact()`. Green after — `bun run check`, 700 tests.

Worth knowing for anything that reuses this shape: the assertion is
`expect(...).toBe("compacting")`, which is not type-constrained, so the test
compiled against the old four-member union and failed at runtime rather than at
typecheck. That is the failure worth having, but it means the test alone does
not tie the controller's spelling of the state to `App.svelte`'s — the `busy`
union and the `svelte-check` leg of `bun run check` are what hold those
together.
