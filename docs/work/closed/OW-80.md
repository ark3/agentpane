# The composer's tools menu is a `<details>`, so it never light-dismisses — clicking away or pressing Escape leaves it open.

`src/client/App.svelte` (`.tools-menu` `<details>`, ~742; `toolsMenu` state ~36; `newConversation`/`compactSession` ~552), `src/client/app.css` (`.tools-menu*`, ~227), `src/client/App.test.ts` (menu tests, ~283-307), `e2e/`

The tools menu OW-72 landed under the composer is a native `<details>`
(`App.svelte:742`), which is a disclosure widget, not a menu: it toggles only on
its own `<summary>`. Clicking anywhere else, or pressing Escape, does nothing,
so it stays open until you click Tools again. Owner observed this on the landed
build and asked for the built-in that dismisses on outside-click (this session).
OW-72 declared the menu's mechanism incidental — "whether it is a `<details>`, a
popover, or a menu element" — so this is finishing that choice, not reopening
the item.

## The fix

The Popover API is the built-in that does it. A `popover="auto"` element plus a
`popovertarget` button gets **light dismiss for free** — outside-click and
Escape both close it, no JS — and puts the menu in the top layer so nothing
clips it. Replace the `<details class="tools-menu">`/`<summary>` pair with a
`<button popovertarget=…>Tools</button>` and a sibling `<div id=… popover>`
holding the two existing menu buttons; the `toolsMenu` `$state` and the
`toolsMenu.open = false` lines in `newConversation`/`compactSession` (`~552`)
go away, since auto-popovers close themselves on activation.

One CSS consequence, load-bearing: the top layer is **not** positioned relative
to the composer, so today's `.tools-menu-list { position: absolute; bottom: …;
left: 0 }` (`app.css:~230`) stops anchoring it to `.prompt-actions`. Keep it at
the left end of the action row with CSS anchor positioning
(`anchor-name`/`position-anchor`) or a small explicit offset — incidental which,
so long as it lands where the `<details>` did.

Incidental: the exact markup, the ARIA (`role="menu"`/`menuitem`) it keeps or
drops, and the anchor mechanism. Load-bearing: outside-click dismisses, Escape
dismisses, and it still sits at the left of the action row.

## Where the test goes — the crux

**jsdom implements no Popover API.** Probed 2026-08-18 against this repo's
jsdom: `element.showPopover` is `undefined` and a `popovertarget` click is a
no-op (`:popover-open` never matches). So the dismiss behaviour **cannot** be
proven in a `src/client/` test, and the three existing menu tests
(`App.test.ts:283-307`), which `fireEvent.click(getByText("Tools"))` then click
a `menuitem`, will break the moment the open step no longer toggles anything.

Split the coverage rather than move it wholesale:

- **Keep the three behavioural assertions in jsdom** — New-conversation inherits
  the selected session's workspace and backend, both entries disable with
  nothing selected, Compact fires `controller.compact`. These do not need a real
  popover; adjust only *how* they reach the items (call `showPopover()` on the
  element directly, or assert on the buttons without an open step) so the
  assertions survive jsdom's missing API.
- **Add the dismiss test in `e2e/`**, the browser vehicle (`bun run
  test:browser`, real `App` mounted in `e2e/harness.ts`, Playwright over
  headless Chromium where the Popover API is real). It is not part of `bun run
  check` — run it by hand. Model it on `e2e/follow.spec.ts`: open the menu,
  click outside, assert it is closed; press Escape from open, assert closed.

## Done when

- The menu dismisses on outside-click and on Escape, verified by a new `e2e/`
  test that fails against today's `<details>` and passes after the swap.
- The menu still opens under Tools and still sits at the left of
  `.prompt-actions`.
- The three behavioural menu tests in `App.test.ts` still assert what they
  assert today, adjusted only for jsdom's missing Popover API.
- `bun run check` passes, and `bun run test:browser` passes.

**Fixed** in 351ff8a: the `<details>` is a `popovertarget` button plus a
`popover` list, so outside-click and Escape both dismiss it with no JS.
`e2e/tools-menu.spec.ts` was watched red against the old markup — "clicking
outside left the menu open", the `menuitem` still `visible` after 14 retries —
and its placement assertions passed in that same red run, which is what makes
them an anchor for the swap rather than a description of the new code. Green
after: `bun run test:browser` 3 passed (48.9s), `bun run check` 699 tests.

Two of the item's assumptions did not survive contact with Chromium, both
checked rather than reasoned about. An auto popover does **not** close when a
control inside it is activated, so the entries carry
`popovertargetaction="hide"`; without them the menu stayed open after Compact.
And jsdom, which implements none of the Popover API, still applies the UA rule
that hides a `[popover]` — so `showPopover()` was never an option and the three
`App.test.ts` menu tests reach their entries with `hidden: true`, assertions
unchanged. Anchoring is `anchor-name`/`position-anchor`, with `display` on
`:popover-open` because an author `display` beats the UA hide rule.

Left open, pre-existing and untouched: `--ap-radius-1` and `--ap-shadow-1` are
not defined anywhere in `app.css`, so the menu's corners have been square since
OW-72 — filed as OW-tesofu.
