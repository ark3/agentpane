# Whether a Codex `plan` item deserves bespoke rendering or stays assistant text, which nothing can judge until a capture exists.

`src/server/adapters/codex/mapping.ts:338-345`, `src/client/render/`

Half of this settled without being asked. `contextCompaction` got bespoke
rendering under OW-72 (`e22740d`) -- a marker drawn by one component for both
backends -- so only `plan` is still open. See OW-6's close note for that half.

`plan` currently folds into assistant text: `mapping.ts:339-345` returns
`assistant(ctx, textBlocks(item.text), ...)`, and its comment states the
position rather than hiding it -- DESIGN leaves plan rendering open ("assistant
text or a custom block") and "Text is the honest minimum: it is literally a
text field." It streams like an agent message, via `item/plan/delta` appending
to `item.text` (`reducer.ts:217-222`), so anything bespoke has to render
partial text too.

**The blocker is that nobody has seen one.** There is no `plan` in any fixture
(`resources/fixtures/{codex,pi}/` hold `text`, `tool-read`, `tool-edit`,
`compact` and `fork`), and `DESIGN.md:653` still lists it among the rows with
no capture. Whether a custom block buys anything depends entirely on what the
text turns out to be -- a checklist worth structuring, or a paragraph that
markdown already renders correctly. Deciding first and capturing second would
be guessing at the answer and then finding evidence for it.

## Revisit when

A `plan` capture exists under `resources/fixtures/codex/`, added by a scenario
in `resources/probes/capture_fixtures.py` the way OW-72 added `compact`. That
is a work-laptop job, since it needs a live Codex turn that produces a plan.
Closing this means looking at the captured text and either building the block
or recording that text was right -- not a UI tweak made in passing.

## Amended 2026-09-30 by OW-zadupu

The capture this card waited on exists: `resources/fixtures/codex/plan.jsonl` and `plan.rollout.jsonl`, captured on the home server on `codex-cli 0.157.1` with `gpt-5.6-luna` by the `plan` scenario in `resources/probes/capture_fixtures.py`, which sends `collaborationMode {mode: "plan"}` on `turn/start`; `docs/MANUAL_TESTING.md`, "Codex fixtures that keep their rollout (OW-zadupu)".
The "work-laptop job" note above is out of date: the home server captures Codex.
Live, the plan was one `plan` item of 180 characters, a three-line numbered markdown list streamed by 42 `item/plan/delta`s, with no `agentMessage` in the turn; `mapItem` draws it as assistant text, which markdown renders as a numbered list.
On disk the rollout stores it as a final-answer assistant message wrapped in `<proposed_plan>` tags, plus a `Plan` `item_completed` record holding the bare text, and the preview draws the wrapped message with its tags showing.
agentpane never sends plan mode, so a `plan` item reaches a user only from a thread another client drove.
So this is no longer blocked on evidence, and the decision is two questions: whether a short numbered list that markdown already renders needs a custom block at all, and whether the preview strips the `<proposed_plan>` wrapper.

## Close note

Decided with the owner on 2026-10-01: no custom block for a Codex `plan`, and no stripping of `<proposed_plan>`. Recorded in `docs/DESIGN.md` under "A `plan` stays assistant text", and in the comment on the `plan` arm of `mapItem`.
Evidence: on `codex-cli 0.157.1` (`resources/fixtures/codex/plan.jsonl`) a plan is a short numbered markdown list that both clients already render as a list. agentpane never sends plan mode, so a plan reaches a user only from a thread another client drove.
The strip question was mostly retired by OW-luvema. Running `extractCodexPreviewTurns` over `plan.rollout.jsonl` gives the bare plan text, built from the `Plan` `item_completed` record. Only a fallback-path rollout (0.150.1–0.154.0) would show the tags, and on 2026-10-01 none of the home server's 119 rollouts contained `<proposed_plan>`.
Reopen if plans grow structure that markdown misrenders, or if a fallback-path rollout carrying the tags turns up.
