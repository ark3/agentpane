# Every timestamp in the UI is UTC, so the reader does offset arithmetic on every line.

`formatTimestamp` renders `date.toISOString().slice(0, 19).replace("T", " ")`,
and its doc comment defends the UTC as deterministic regardless of the viewer's
timezone. That was inherited from the session list, and OW-67 then reused it for
all three transcript placements, so today it is the format of every time this UI
shows. The determinism buys nothing: the viewer is one person on one machine
reading their own sessions, and nothing here travels between people. It costs an
offset calculation per line, and it is actively wrong in the two-machine setup —
the home server serves the transcript, the laptop reads it, and the *browser's*
zone is the one that matches the reader's wall clock whichever machine served
the bytes. Decided 2026-08-18 by the user, after using what OW-67 landed.

Same shape, `YYYY-MM-DD HH:MM:SS`, same single shared formatter, rendered in the
browser's local zone. `toISOString` cannot produce it — pad the local components
(`getFullYear`, `getMonth` + 1, `getDate`, `getHours`, …) rather than reaching
for `toLocaleString`, whose output shape moves with the locale. **`timestampIso`
stays UTC**: it feeds `<time datetime=…>`, where an absolute instant is exactly
what the attribute is for. Do not "fix" it to match.

The blast radius, measured 2026-08-18: four hardcoded strings, at
`time.test.ts:23` and `:27`, `tools.test.ts:181`, and `App.test.ts:483` (the
pre-existing session-list assertion). Everything else asserts *through* the
formatter — `Transcript.svelte.test.ts:111,119` compare against
`formatTimestamp(...)` — and follows it for free, which is what OW-67's
centralizing bought. The tests must pin `TZ` to a **non-zero offset**: pin it to
UTC and all four literals keep passing untouched, and nothing would have proven
local rendering at all. `vite.config.ts` has no `env` today and
`vitest.setup.ts` is client-only, so the `test` script in `package.json` is the
seam that covers both projects — but whichever seam you pick, verify it actually
reaches `Date` under Bun + vitest instead of assuming a mid-process
`process.env.TZ` is honoured.

Done when those four literals carry their *shifted* values under the pinned
zone and each was watched fail against the old formatter first; when the session
list and all three transcript placements still render identically to each other
(the epoch-ms/ISO equality in `time.test.ts` is the pin for that — keep it);
when `bun run check` is green; and when `time.ts`'s doc comment argues the local
rationale instead of the UTC one it argues today. Load-bearing: local time, one
formatter for both surfaces, `datetime` left absolute, a non-UTC zone pinned in
tests. Incidental: which zone, and how the local components get padded.

**Fixed** in 147475f: `formatTimestamp` pads local components instead of
slicing `toISOString`, and the `test`/`test:watch` scripts pin
`TZ=Asia/Kolkata` — +05:30, no DST, so a half-hour offset moves the minutes as
well as the hour and an hour-only fix would still fail. All four literals were
watched red against the old formatter under that zone first (`03:44:15` →
`09:14:15` at `time.test.ts:23` and `:27` and `tools.test.ts:181`, `12:34:56` →
`18:04:56` at `App.test.ts:483`), and the script env was verified to reach
`Date` in both vitest projects by a throwaway probe in each of `src/shared/`
and `src/client/` reporting `getTimezoneOffset() === -330`. The epoch-ms/ISO
equality pin still holds, so the session list and all three transcript
placements stay identical; `timestampIso` is untouched and still UTC. `bun run
check` green, 677 tests.
