# A dispatched subagent is told to commit somewhere it cannot, so it commits nothing and the parent retypes its diff onto `main` by hand.

`.claude/skills/execute/SKILL.md:26-33`, `AGENTS.md` "Landing work"

Step 2 sends it into its own worktree and opens by telling it to read
`CLAUDE.md`, which leads to `AGENTS.md`: *"Commit directly on `main` as the work
is done... No branch, no PR."* That instruction is unexecutable from a worktree
checked out on a branch that is not `main`, so the safe reading is to leave
everything uncommitted — which is what happens. The branches never advance past
their starting commit, and step 4 "Land" is really the parent re-applying a
diff: `git log --merges` shows nothing since the `OW-` era began, and the close
notes say it outright (OW-43, OW-45: *"the patch applied cleanly and `bun run
check` was re-run on `main`"*). Nine worktrees accumulated in this checkout
before being removed by hand at the owner's request, every one of them holding
work that had already landed by other means. Fix both halves: give the dispatch
prompt an explicit instruction to commit on its own branch, and scope
`AGENTS.md`'s rule so it reads as addressed to the session agent rather than to
everything that loads it — otherwise the next dispatched agent hits the same
contradiction. Then step 4 becomes `git cherry-pick`, `git commit --amend` for
whatever review changed, `bun run check`, `git worktree remove`, `git branch
-D`. **Load-bearing:** the amend, because step 3 review deletes out-of-scope
work and a bare cherry-pick would land the unreviewed version; and cherry-pick
rather than `git merge`, because history on `main` is linear and a merge commit
per row breaks that. **Incidental:** whether the worktree is torn down before or
after the close commit. Note this does not by itself fix OW-58 — it converts a
stale worktree from a paragraph of explanation into a cherry-pick conflict,
which is an improvement but a different one. Done when an execute session lands
a row this way and its close note carries the cherry-picked sha, with `git
worktree list` and `git branch` each showing only `main` when the session ends.
Raised by a second agent reviewing the workflow, 2026-08-16.

**Fixed** in `9b786a6`, and the fix was exercised by the session that landed it.
The dispatched agent was told in its prompt that it commits on its worktree's
branch and cannot commit on `main`; it committed `147d3f3` on
`worktree-agent-a3c851d743d310398`, and that commit was cherry-picked onto
`main` as `9b786a6` — the first dispatched work in the `OW-` era to reach `main`
as its author's own commit rather than as a retyped diff. `git worktree list`
and `git branch` each show only `main`. **The amend was not exercised:** review
found nothing out of scope and nothing to change, so `git commit --amend` had no
work to do; step 4's amend clause is written but still unproven, and the first
row whose review deletes something is the test of it. `bun run check` was not
run — both files are docs, and `AGENTS.md` exempts docs-only commits. **One
observation this run produced, which belongs to OW-58 and is deliberately not
acted on here:** the dispatched worktree was cut 19 commits behind `main`
(`9ad0a6d`, against a tip of `c04f26c`) and the agent fast-forwarded it by hand
before editing, which is why the `AGENTS.md` line numbers it was given were off
by six. That is a third instance of the staleness OW-58 records, and a much
larger one than the two it cites; recording it as live-run evidence in
`MANUAL_TESTING.md` is OW-58's job, not this row's.
