# A freshly-created session's sidebar entry keeps its placeholder label after the first prompt and never catches up without a full page reload.

Reported live: create a session, submit the first prompt, and the row keeps
showing the raw ref; reloading the browser is what finally shows real text. The
label is `summary.preview || ` `${backend} ${id}` ` (`App.svelte:460`), and
`summary.preview` is server-supplied — `parsePiSession` fills it from the
**first** user text message in the stored JSONL and `break`s (`pi.ts:69-94`). A
new session has no such file until the first prompt materialises it, and the
only re-list tied to that moment is the single `sessionsChanged()` fired inside
`#adoptRef` (`session-manager.ts:270`), which the client answers with exactly
one `refreshSessions()`. Nothing re-triggers another list for this session — no
event fires on turn completion, only on create/attach/rename/close
(`session-manager.ts:185,218,270,386,445`). So if that one fetch reads the file
before Pi has flushed the user turn, `preview` stays `null` with no second
chance. **Fix at render, and do not diagnose the race:** when `summary.preview`
is null, fall back to the first `role:"user"` message's text from the live view
the client already holds
(`view.state.sessions[sessionKey(summary.ref)].messages`) before falling back to
the ref. Three things make this the cheap correct fix, all checked at the
source: (a) it needs no extra fetch and no new broadcast — a `sessionsChanged()`
on turn end would cost a full-corpus walk+parse per turn (OW-23); (b) it is
immune to the write-ordering question entirely, because the client sent that
text and holds it in memory with certainty, whatever the file has; (c)
first-user-message is *exactly* the server's own preview semantics
(`pi.ts:82-88`), so the fallback and the server value that eventually arrives
agree rather than flickering between two different strings. Safe across the
rename because the `"renamed"` reducer re-keys `state.sessions` from the virtual
key to the real one (`session-state.ts:96-98`), so `sessionKey(summary.ref)`
still finds the view afterward. No truncation logic needed — `.session-preview`
already ellipsizes (`app.css:155`). Deliberately **not** covered, and not
defects to chase from this row: a session created in another browser tab still
shows a stale label until something re-lists it, and whether Pi flushes before
`submit()` resolves stays unanswered — this fix makes that question stop
mattering for the observed symptom. Done when: a failing-first client test
drives `App` through the real SSE order (`sessions-changed`, `renamed`,
`snapshot` — `broadcaster.ts:137-147`) with a summary whose `preview` is `null`
and a snapshot carrying a user message, asserting the sidebar row shows that
message's text rather than the ref; and the existing behavior for a session with
no messages and no preview — the ` `${backend} ${id}` ` fallback — still holds.

**Fixed** in `4ef9c72`, at render as the row directed: `sessionLabel(summary)`
in `App.svelte` returns `summary.preview`, else `firstUserText(summary)` — the
first `role:"user"` message in `view.state.sessions[sessionKey(summary.ref)]`,
non-empty `type:"text"` blocks joined on a space and trimmed — else the
`${backend} ${id}` ref. Being a plain function called from the template it
re-reads `view` reactively, so the row upgrades to the server preview the moment
one arrives. Verified in review that the fallback matches `parsePiSession`'s
semantics exactly (`pi.ts:83-88`: same filter, same `" "` join, same trim),
differing only by `trimPreview`'s truncation, which the row deliberately left to
`.session-preview`'s existing ellipsis; Pi's parser applies no synthetic-block
filtering (only `codex.ts` has `isSyntheticBlock`), so there is nothing there
for the fallback to mirror. Pinned by a new `App.test.ts` case that replays
`sessions-changed` -> `renamed` -> `snapshot` through the real
`reduceServerEvent` rather than hand-assembling the end state, with `preview:
null` on the summary. Confirmed failing first: the pre-fix component could not
be found by the row's accessible name and the printed DOM showed `pi
/home/u/.pi/sessions/abc.jsonl`. The `${backend} ${id}` fallback for a session
with no messages and no preview still passes unchanged. `bun run check` green at
610 tests.
