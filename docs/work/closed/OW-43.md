# OW-38's preview extractors inherit `readLinesLfOnly`'s enumeration-sized caps, so the preview silently ends well before the real end of a long session.

`src/server/sessions/pi.ts:122`, `src/server/sessions/codex.ts:196`, `src/server/sessions/line-reader.ts:31-32`

`extractPiPreviewTurns` and `extractCodexPreviewTurns` both call
`readLinesLfOnly(filePath)` with no options, so they get `DEFAULT_MAX_LINES =
200` / `DEFAULT_MAX_BYTES = 512 * 1024` (`line-reader.ts:31-32`) — caps sized
for `parsePiSession`/`parseCodexSession`'s enumeration path, which reads just
far enough to find one message and `break`s (D9's cheap-listing goal). The
preview extractors don't `break`; they iterate to (what should be) the end of
the file, so on any session past 200 lines or 512KB they just stop mid-file with
no error and no signal — fewer turns than the session actually has. Attaching
doesn't share this cap and shows everything, which is the discrepancy reported
live: the preview pane ends early, hitting Attach shows the whole transcript
once the subprocess is up. No existing test catches this — `line-reader.test.ts`
pins the caps directly, and `preview.test.ts` (222 lines) has no fixture
anywhere near 200 lines / 512KB. Fix: give the preview extractors their own
unbounded (or much larger, with truncation surfaced to the client rather than
silent) read, distinct from the enumeration callers' bounded one —
`readLinesLfOnly` already takes `maxLines`/`maxBytes` as options, so this is
plumbing, not a rewrite. Done when: a failing-first test writes a stored session
past both current defaults and asserts the preview contains turns from past line
200 / byte 512KB, and the existing enumeration tests (which rely on the bounded
read staying cheap) still pass.

**Fixed** in `acb0060`: `extractPiPreviewTurns` and `extractCodexPreviewTurns`
now pass `{ maxLines: Infinity, maxBytes: Infinity }` to `readLinesLfOnly`; the
enumeration callers keep the no-args bounded read and their cost assertions
unchanged. Unbounded was chosen over "larger, with truncation surfaced"
deliberately — attaching already shows the whole transcript, and closing that
discrepancy is the row's entire point, so no protocol field and no truncation
signal were added. Pinned by one new `preview.test.ts` case per backend, each
synthesizing a 301-line / ~900KB store-format fixture (300 alternating turns of
~3KB) and asserting all 300 turns return, including `turns[250]`, which sits
past both caps. Confirmed failing first with the extractor change stashed out:
both failed `expected 167 to be 300` — the 512KB byte cap biting first, at
roughly line 167. `bun run check` green at 612 tests. The executing worktree was
cut behind `main`; the patch applied cleanly and `bun run check` was re-run on
`main`, where review also corrected the two test names, which cited OW-47
instead of this row.
