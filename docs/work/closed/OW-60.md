# The transcript navigation affordance is anchored to the scrolled conversation instead of the pane viewport, and it needs to become a right-rail navigation pill.

Today the only affordance is the `showJumpToLatest` button rendered inside
`.conversation` (`App.svelte`, `.jump-to-latest` in `app.css`), so when the
reader is mid-history it can scroll off-screen with the content it is supposed
to help navigate. Replace it with one always-present, tall narrow pill fixed to
the right of the conversation pane, outside the bordered transcript so it never
obscures content; localhost-only and owner-only means no
responsive/discoverability work is required here. Four stacked segments,
icon-only: double-chevron up = start, single-chevron up = previous user input,
single-chevron down = next user input, double-chevron down = end. `Prev`/`next`
are relative to the first user turn at or below the viewport top, not "most
visible"; `start` and `end` mean true top/bottom of the scroller. Grounding for
the executor: user turns already render as DOM landmarks with stable
`data-index` and `data-role="user"` in `Message.svelte`, and `transcript.ts`
preserves those original indices even in reading view specifically so shell
scroll logic can keep targeting them. Keep all navigation logic in the shell
beside `handleConversationScroll`/`jumpToLatest`; these jumps are manual reading
actions, so like a manual scroll they must never arm follow mode. Done when
jsdom pins the button-state and target-selection logic (including disabled
states at the ends and around consecutive assistant/tool messages), and `bun run
test:browser` is extended or replaced with a real-browser check that the
right-rail control stays visible while the conversation scrolls and that its
jumps land on the intended user turns without regressing follow-mode behavior.

**Fixed** in `848d8c2`. The row's grounding was re-checked against the source
before dispatch and had not drifted. `Message.svelte` was in the row's Where and
needed **no change** — its `data-role="user"`/`data-index` landmarks were
already what the rail needed. The rail is a third `auto` grid column of `.shell`
(`grid-area: rail`, `align-self: center`), a sibling of `.conversation` rather
than a child, which is what makes it immune to all three of the old button's
problems at once: it cannot scroll away, cannot sit over the transcript, and
cannot count toward the `scrollHeight` the follow-mode math reads. Target
selection: the pivot is the first `[data-role="user"]` node whose `anchorTop` is
at or below `scrollTop` (4px slack); `prev` is the turn before it, `next` the
turn after. Because every jump parks its target's top edge on the viewport top,
that target becomes the next pivot, so repeated clicks walk one user turn at a
time in either direction. With no pivot (every turn above the viewport top)
`prev` is the last turn and `next` is null. `start`/`end` are the scroller's
true ends, never the first/last turn. Disabled: `start` = atTop, `prev` =
atTop || no earlier turn, `next` = atBottom || no later turn, `end` = atBottom.
**Judgement recorded, not reversed:** the `atBottom` half of `next` goes beyond
the row's literal wording and is deliberate — the last screenful can hold user
turns the scroller can never bring to its top, where `next` would otherwise stay
live while clicking it moved nothing; that case has its own jsdom test. All four
clear `anchorIndex` and never arm follow; `navigate` also writes back
`state.top` after jumping, which the old `jumpToLatest` did not, so a session's
remembered scroll position no longer goes stale across a switch. `.conversation`
loses `position: relative`, orphaned by deleting the absolutely-positioned
button — which also restores what `anchorTop`'s own comment claims it relies on
(that neither element is a positioned offsetParent). **One pre-existing defect
was found and fixed here because it blocked the rail entirely:**
`applyScrollTop` clamped only at zero, so the session-switch effect's
`applyScrollTop(el, el.scrollHeight)` — always a full `clientHeight` past the
bottom — passed the no-op guard, armed `suppressScrollHandling`, then assigned a
value the browser clamped to no change, firing no `scroll` event and stranding
the flag, which then swallowed the reader's next genuine scroll. Instrumented in
Chromium: after attach, a 4960px scroll fired its event and was discarded while
the rail kept reporting the reader was at the top. Now clamped to
`scrollHeight - clientHeight`. This forced one existing jsdom expectation from
700 to 200 —
that 700 was pinning the jsdom artifact (no layout, so no clamp) that no browser
ever holds. Related to but distinct from OW-48, which is about two events
against one flag rather than zero events against an armed one. Four new jsdom
tests plus one new browser test, every one confirmed failing first: nav
candidates widened to all `[data-index]` (`expected +0 to be 1000`), pivot
predicate flipped to strictly-below (`expected 2000 to be 1000`), `end`
retargeted to the last user turn (`expected 2000 to be 2100`), `start` never
disabled, `next` losing its at-bottom condition, a rail jump arming follow
(`expected 900 to be 500`), and `prev`/`next` landing 40px off the pane top
(`next did not land on user turn 2: 40.05 > 2`). One break initially passed for
the wrong reason — an unmocked rect reads 0 in jsdom, which reconciled back to
the position the jump had already left behind — and the assertion was
strengthened until it went red. The browser test pins the two things jsdom
structurally cannot see: the rail is not a descendant of `.conversation`, and
its box does not move when the transcript scrolls under it. **The defect itself
was reproduced there**: with the rail moved back inside the scroller and the
structural assertion bypassed, scrolling moved it from y=9888.9 to y=5124.9 —
4764px, straight off-screen. It also re-checks that a submit still arms follow
after the rail has been driven. `e2e/follow.spec.ts` was extended, not replaced;
the OW-47 test is untouched. `bun run check` green on `main` (643 tests) and
`bun run test:browser` green (2 tests). **Unproven, deliberately:** the `@media
(max-width: 42rem)` fallback lays the rail down as a horizontal row between
conversation and prompt. Updating that media query was forced — the new grid
area has to appear in the single-column `grid-template-areas` or it auto-places
— but the result was never rendered at that width, because the row waived
responsive work as out of scope for a localhost-only owner-only tool. Not yet
looked at in a browser by the owner; the presentation verdict (rail chrome, icon
weight, vertical centring) is theirs.
