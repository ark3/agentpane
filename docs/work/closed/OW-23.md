# `SessionIndex.get(ref)` fully parses every session file in both stores on every cold attach.

`src/server/composition.ts:14` (`get`), `src/server/sessions/index.ts:82-98` (`listSessions`)

`get` calls `listSessions()` with no args, which reads and parses the full
content of every `.jsonl` file in both stores (line 94) *before* any `cwd`
filter is applied (lines 96-98) — so passing a `cwd` filter through, this row's
previous fix suggestion, would not help: the filter only trims the array handed
to `.find()`, after the expensive walk+parse already happened.
`session-manager.ts:286` calls `get` for any session not already in the process
table, so every cold attach pays the full-corpus cost — ~0.28s against finding
19's 973-file census, growing with the corpus. **Promoted by D12:** idle/LRU
eviction makes cold reattach routine, so this moves onto the hot path — fixing
it is a prerequisite to landing OW-33/OW-34, not a follow-up. Real fix, dispatch
on `ref.backend` inside `get` instead of delegating to `listSessions`: for Pi,
the ref *is* the file path (D9), so `get` should `stat` + `parsePiSession`
(`src/server/sessions/pi.ts`) that one file directly, no walk at all. For Codex,
the ref's UUID is embedded in the filename (verified against a real file:
`~/.codex/sessions/2026/08/12/rollout-2026-08-12T22-10-29-019ff8e2-...-c5.jsonl`)
— use `findJsonlFiles` (`src/server/sessions/walk.ts`, a `readdir`-only walk
with no file reads) to find the filename match, then `parseCodexSession` only
that one file. Done when: a test seeding N session files across both backends,
calling `get()` for one Pi ref and one Codex ref, asserts (via a read-call
counter or spy on the parse functions) that only the matching file's content is
read — not all N — and the existing cold-attach integration test still passes.

**Fixed** in `bfc5eda`: `createSessionIndex().get` now delegates to a new
`getSession(ref)` in `src/server/sessions/index.ts` that dispatches on
`ref.backend` and reads exactly one file — Pi's ref is the path (D9), so a
direct `stat` + `parsePiSession` with no discovery at all; Codex's uuid is in
the filename, so a `readdir`-only `findJsonlFiles` walk locates the one match
and only that file is parsed. `listSessions` itself is untouched. The filename
matcher `fileMatchesThreadId` moved out of `sessions/preview.ts` into
`sessions/walk.ts`, so the OW-38 preview path and this lookup share one
anchoring rule (id as a trailing name segment, so a longer id containing this
one does not false-match) rather than two copies; `walk.ts` is the home because
`preview.ts` imports `SESSION_ROOTS` from `sessions/index.ts`, so the reverse
import would cycle. Pinned by a new `composition.test.ts` case that seeds 6 Pi +
6 Codex files, spies on both parsers, and asserts only the two matching paths
were ever handed to one. Confirmed failing first twice — by the executing agent,
and again in review by restoring the old whole-corpus `get`, which recorded 12
Pi reads (6 files x 2 `get` calls) against the expected 1. `bun run check` green
at 613 tests. Two notes for whoever lands OW-33/OW-34, which this unblocks:
`get` no longer verifies that the returned summary's ref equals the requested
one (the old `.find()` matched on `sessionKey`; the Codex path now trusts the
filename uuid, as `preview` already did), and a Pi ref is read as a path with no
check that it sits under the Pi store — both properties the OW-38 preview path
established first, on a loopback single-user server. A `findFiles` injection
seam the implementation added was removed in review: no test used it.
