# What a fork's returned ref means.

`POST .../fork`

Pi's `fork` rewinds the active branch of the *same* session file and returns the
same ref; Codex's `thread/fork` mints a new thread id. The route hands that ref
straight back, so on Codex the browser will receive a ref for a session the
process table has never heard of and holds no adapter for — and the on-disk
index may not see a thread the backend has not flushed. Settle it with the Codex
adapter, not before.

**Fixed** in cfcfe0b: the Codex half settled live (codex-cli 0.148.0), the
`fork_probe.py` `codex_new_session` cell now recording it. The route's fear was
disproven: `thread/fork` flushes the forked rollout to disk *before any turn is
driven* (`forked_on_disk_before_turn: true`, `thread_read_forked_before_turn_ok:
true`, `forked_from_id` set), so a fresh attach on the returned ref finds it —
the index does not lag. The two backends are asymmetric and both are absorbed by
`SessionManager.fork` through `#adoptRef`: Pi's fork moves the same process's
active file (re-key + `renamed`; see OW-pifowo), while Codex mints a new thread
the current adapter is not driving, so its own ref is unchanged (`#adoptRef`
no-ops) and the returned ref points at the freshly-flushed thread. The route now
forks through the manager and its comment records this rather than the old
"UNSETTLED" note. Test: `session-manager.test.ts` gains the Codex-style case
asserting no re-key and no `renamed`. See `docs/MANUAL_TESTING.md` "Settling the
fork's returned ref".
