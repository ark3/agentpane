# An assistant turn spends two rows on its footer, buttons then timestamp, where a user turn spends one.

`src/client/render/Message.svelte` (assistant `.meta`, ~`:82`), `src/client/render/Block.svelte`, `src/client/render/BlockActions.svelte`, `src/client/render/Transcript.svelte.test.ts`, `src/client/App.test.ts:444`, `e2e/harness.ts:163` plus a new spec under `e2e/`

Observed 2026-08-18 in preview mode: a user turn puts its timestamp and its
copy/expand buttons on one row, opposite ends; an assistant turn puts the
buttons on a row of their own and the timestamp on the row below. Two lines
carrying about six words, once per turn, down the whole transcript.

## Why it happens

The two rows are two components in two flex containers that never learned about
each other.

- `Message.svelte`, assistant arm: `<p class="meta">` (time, model, effort,
  tokens, cost) is a **sibling of `.body`**, left-aligned, message-level.
- `BlockActions.svelte`: each text block renders its own `.actions` row
  **inside `.body`**, `justify-content: flex-end`.

The user arm has no `.meta` at all. `Message.svelte` passes `message.timestamp`
into the *first* block's `BlockActions`, where `.time { margin-right: auto }`
parks it at the left end of the button row — OW-67's third placement, which was
sequenced after OW-63 built that row. The assistant never got the same
treatment because it already had a meta row, so nobody merged the two.

Preview makes it maximally visible rather than being a preview-only bug:
`preview.ts` (`previewMessages`) builds each assistant turn as exactly one text
block with `model = backend` and zero usage, so *every* preview assistant turn
hits the both-rows-present case.

## The shape wanted

One footer row per assistant turn: meta facts at the left, copy/expand at the
right, the same row a user turn already uses. Either implementation is fine —
hand the meta content down to the last text block's `BlockActions` (the prop
channel for `timestamp` already exists, `Message` → `Block` → `BlockActions`),
or stop that block rendering its own actions and have `Message` render the
merged row. Pick on which reads cleaner once you are in the files; the
observable outcome is what is load-bearing, not the direction of the plumbing.

## Where it must degrade instead

An assistant turn's last block is not always text. Agreed 2026-08-18: the
merged row degrades to whichever half exists, so the change never *adds* a row
relative to today.

- Last block is a `toolCall`, `thinking` or `image` — no `.actions` row to merge
  with, so `.meta` renders standalone exactly as today.
- Streaming, `stopReason === "pending"` — no `.meta` renders yet
  (`Message.svelte`'s existing guard), so the actions row stands alone.
- Multi-block turn (text → toolCall → text) — only the **final** text block's
  row absorbs the meta; earlier text blocks keep bare button rows. Accepted as
  good enough for now, not as the end state.

The error/aborted banner stays its own element between body and footer.

## Two consequences to decide, not to discover

`.actions` carries `opacity: 0.55` (rising to 1 on hover/focus-within) and
`user-select: none`. Meta text moved into that row inherits both, where today
assistant meta is always at full `--ap-fg-subtle` and is selectable.

The dimming is fine and is what the user row already does. The selection loss
is a real change: the token count and cost stop being copyable with a
drag-select. `user-select: none` is there deliberately so the button glyphs do
not land in a copy of the block — that part must stay. Whether the meta text
inside the row keeps selection is the executor's call; make it explicitly and
say which way in the commit message.

## Not scoped to preview

These components render preview and attached identically, so the fix lands in
both; do not thread a `previewing` flag through the render tree to avoid that.
Attached mode has its own footer oddities, reported but not yet diagnosed or
described — out of scope here, and expected to be partly relieved by this
change rather than addressed by it.

against today's markup first.

   a finished `stopReason` renders **one** footer row, with `.meta` inside the
   trailing `[data-block-actions='text']` element.
2. The existing placement assertions still resolve unchanged rather than being
   rewritten to match new markup: `.meta time` (`Transcript.svelte.test.ts:110`,
   `:171`), `[data-block-actions='text'] time` for the user row (`:119`,

   (`App.test.ts:444`). Keep the `.meta` class on whatever element carries those
   facts, wherever it now renders.
3. Each degradation above has its own test: toolCall-last renders `.meta` with
   no merged row, a pending turn renders the actions row and no `.meta`, and a
   text → toolCall → text turn renders exactly one `.meta`, on the last text
   block's row.
4. Layout truth, in a browser, because jsdom cannot see it: one Playwright
   assertion that the meta and the buttons share a row — equal
   `getBoundingClientRect().top` within a pixel, or overlapping y-ranges. This

   turn with no timestamp, extended with a completed assistant turn and

   reaches preview mode without a click. Runs under `bun run test:browser`,

5. A before/after screenshot of a preview transcript in `MANUAL_TESTING.md`: the

**Fixed** in 35ca4da: `Message.svelte`'s assistant `.meta` is now a `{#snippet}`
handed down the existing `Message` → `Block` → `BlockActions` prop channel, so
it renders inside the trailing text block's `.actions` row instead of a row of
its own — meta at the left (`margin-right: auto`), copy/expand at the right,
the row a user turn already had. It rides that row only where one exists, so
the change never adds a row: a turn ending in a toolCall keeps a standalone
`.meta`, a pending turn keeps a bare button row, an earlier text block in a
multi-block turn keeps a bare row too. Selection was decided the other way from
the row's default — `.meta` opts back into `user-select: text`, because
`user-select: none` is there to keep button glyphs out of a copy of the block
and the token count and cost are facts a reader quotes. Five jsdom assertions
in `Transcript.svelte.test.ts` cover the merged row and each degradation, and
`e2e/footer-row.spec.ts` measures both boxes in a real browser (y-ranges
overlap *and* centres agree, either alone passing for a stacked meta) off a
`harness.ts` `preview()` now serving a completed, stamped assistant turn. The
three placement assertions went red against the old markup and the two
degradation ones against deliberately wrong merge rules. Done-when #2's
existing assertions resolve unchanged; the one test the item did not anticipate
— "does not stamp an assistant's text block", asserting no `<time>` in any
block action row — was rewritten to the claim behind it, exactly one `<time>`
per assistant turn, rather than deleted. Before/after captures in
`docs/MANUAL_TESTING.md` (new `docs/images/`, the repo's first): the previewed
`.transcript` is 228px tall before and 203px after, 25px per assistant turn.
Where the item's prose disagreed with itself — "the shape wanted" says the last
*text* block, the agreed degradation section says a toolCall-last turn keeps a
standalone `.meta` — the degradation section was taken as authoritative.
