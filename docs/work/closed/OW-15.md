# A `success:false` response to the post-admission `get_state` probe is swallowed with no diagnostic anywhere: `handleResponse` rejects the caller and returns before the `emitError` fallback.

Pi process shell

Keeping it off `onError` is right — the turn was admitted and is running — but a
*persistent* probe failure leaves the session keyed to its `virtual:` id
indefinitely, silently.

## Close note

Moot, checked at b758f98 by OW-geselo.
The post-admission `get_state` probe in `PiAdapter.submit` (`src/server/adapters/pi/process.ts`) runs only under `if (!this.idResolved)`, and its comment records that Pi 0.84.1, 0.85.1 and 0.87.1 all named the session file at start (HANDOFF finding 41, MANUAL_TESTING OW-bohodu), so on every measured version the probe never runs.
`idResolved` can be false there only if `start()`'s own `get_state` answered with no `sessionFile`, which that field's optionality in `pi/protocol.ts` permits and no measured version did; a failed start-time `get_state` rejects `start()` loudly instead, and `src/server/adapters/pi/spawn.ts` never passes `--no-session`.
A failed probe is still silent (its `catch {}` swallows everything), but each later prompt probes again, so one failure does not strand the session on its `virtual:` id.
The hypothetical is covered by the test "resolves the id after the first prompt when start's get_state named no file"; reopen if a Pi version stops naming the file at start.
