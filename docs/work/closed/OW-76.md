# A read-only preview is a one-shot snapshot: the session grows on disk and the pane never notices, with no sign it has gone stale.

`src/client/controller.ts` (`preview` ~`:222`, `refreshSessions` ~`:110`, `dispose`), `src/client/App.svelte` (`previewing` `:111`, the Refresh button `:615`), a new pure delay module (e.g. `src/client/preview-poll.ts`) plus its test, `src/client/controller.test.ts`, `src/server/sessions/pi.ts:119` and `codex.ts:192` for why the change test is what it is

`view.preview` is written in exactly one function, `controller.preview(ref)`, so
a preview only ever changes when something calls it: a sidebar row click
(`App.svelte:626`) or the auto-select effect (`App.svelte:473`, on workspace
change or startup). Nothing re-fetches while a preview is on screen. There is no
polling anywhere in the client — the sole `setTimeout` (`App.svelte:196`) is a
rAF fallback for follow scheduling. A previewed session is by definition not
attached in this client, so it receives no `snapshot`/`upsert` SSE events at
all, and `sessions-changed` (emitted only on create, attach, rename, close and
fork — `session-manager.ts:185,218,270,386,445`, `app.ts:246`) is not emitted
when a session's transcript file merely grows. So a session running under its
own CLI, or driven from another agentpane client, is invisible here until the
row is clicked again or the page reloaded.

Worse, the control that looks like the fix is not one: **Refresh**
(`App.svelte:615`) calls `controller.refreshSessions()`, which re-lists
summaries and does not touch `view.preview`. Pressing it updates the sidebar and
leaves the transcript below it stale.

## What to build

A preview keeps itself current, client-side only. No protocol change, no new
server event, no widening of `SessionPreviewResponse`.

1. **A `refreshPreview()` on the controller**: re-fetch `api.preview` for the
   ref already in `view.preview`, replace `turns`, and report whether anything
   changed. It must not change `selected`, must no-op when `view.preview` is
   null, and must not resurrect a preview when the user attached or switched
   mid-fetch — `controller.preview` already has the `selectionIntent` guard for
   exactly this, so reuse it rather than inventing a second mechanism.
2. **Refresh refreshes the preview too**: `refreshSessions()` also calls it.
   That also picks up `sessions-changed`, which routes through the same function
   (`controller.ts:181`).
3. **Refresh on returning to the tab**: a `visibilitychange` / `focus` listener
   calls `refreshPreview()`. This is the common loop — look at the terminal,
   come back to the browser.
4. **An adaptive poll while a preview is showing and the tab is visible.**
   Start at **16s**. Any refresh that finds a change — timer, focus, or the
   Refresh button — sets the interval to **1s**. Each *timer* tick that finds no
   change **doubles** it, to a **ceiling of 16s** (1, 2, 4, 8, 16, then flat).
   The floor is 1s by construction. Never poll a hidden tab; stop on attach, on
   switching away, and on `dispose`.

Prefer a chained `setTimeout` over `setInterval`: the delay changes on every
tick, and a chained timeout cannot overlap a slow fetch.

## Where the pieces live, and why it is not a free choice

`controller.ts` today contains **no** reference to `window` or `document` —
verified by grep, not assumed — and this change must not be what makes it depend
on the DOM. So:

- The `visibilitychange` / `focus` listeners live in `App.svelte`, which already
  owns effects and lifecycle.
- **The timer and `refreshPreview()` live in the controller**, with visibility
  *injected* — a predicate passed to `createController`, or an argument the
  caller supplies — rather than read from `document` inside it.
- The delay arithmetic lives in its own module, per above.

That split is not merely tidy: it is what makes the poll testable. The
alternative — App.svelte owning the timer — puts these tests in
`src/client/App.test.ts`, where they would run against `FakeController`, whose
`preview` "only records the call, which the real one does" not do
(`App.test.ts:54`, and the comment at `:160`). A poll test written against that
fake asserts call counts while never seeing `turns` replaced, which is precisely
the class of defect OW-42 exists to describe and OW-41 already landed green
once. Drive the real `createController` with a fake `api`.

**Keep the schedule pure and separately tested.** A function of (current delay,
did-it-change) to the next delay, in its own module, so the ceiling and the
doubling are asserted without a timer race. The timer that drives it is the part
that needs fake timers; the arithmetic is not.

## Decided, not open — do not helpfully improve these

All from the owner, 2026-08-18, in the session that filed this.

- **The change test is `turns.length`.** Both extractors map **one JSONL record
  to at most one turn** (`pi.ts:119`, `codex.ts:192` — neither coalesces
  consecutive assistant records), and a JSONL only appends, so a turn's text
  never grows in place and any new content is a new turn. Do **not** compare the
  last turn's `timestamp` instead: that field is *optional*
  (`...(timestamp ? { timestamp } : {})`, OW-71), so a session whose records
  carry none would compare `undefined` to `undefined` and never look changed,
  and nothing stops two records sharing a second. A rewrite (fork, or OW-72's
  compaction) changes the length too, including by shrinking it.
- **No auto-scrolling.** New turns append below the fold and the pane does not
  move. No sticky-bottom, no tail-following; the nav rail's Jump-to-end is the
  affordance. Follow mode arms only on submit (`armFollow`, `App.svelte:381`)
  and a preview never submits — leave that alone.
- **A user gesture never backs the interval off.** Manual Refresh and focus
  refreshes may drop it to 1s on a change, but a gesture that finds nothing
  leaves the delay where it was. Backoff measures how quiet the *file* is, and a
  keypress is not evidence about that.
- **The cost of 1s polling is accepted.** Each poll is a full read and parse of
  the whole file, deliberately unbounded so the preview reaches the real end
  (`pi.ts:122`, OW-43), and the fast rate coincides with the largest file — an
  actively streaming session. Measured nothing: this clone holds one 0.1MB Codex
  session and no Pi store, and `DESIGN.md:300`'s numbers are file counts, not
  sizes. The owner's call was "accept it; nothing is permanent here." If it does
  hurt on the machine with real data, *that* is the evidence for a cursor-based
  incremental fetch, which is not to be built speculatively.
- **The sidebar goes on lagging.** The poll must not re-list sessions —
  `listSessions` walks both stores with no cache by design (`index.ts:5-10`) —
  so the previewed row's timestamp stays stale while the transcript updates.
  Refresh brings both into line. Accepted.
- **Rejected as bigger than the defect:** watching the file server-side and
  pushing a new SSE event (previews are stateless today, `app.ts:201-208`, so
  the server would have to track who previews what), and adding a cursor to
  `SessionPreviewResponse` (a D11 interface widening, which OW-50 already
  refused for its own reasons). Also rejected: printing the snapshot time in the
  pane, and polling `listSessions` to watch `updatedAt` advance.

## Done when

`bun run check` is green and each new assertion has been watched fail first.

1. The pure schedule module: starts at 16s; a change gives 1s; successive quiet
   ticks give 2, 4, 8, 16, and 16 again — the ceiling holds rather than doubling
   past it.
2. Controller test — the **real** `createController`, never `FakeController`
   (above) — with fake timers and a fake `api` counting `preview` calls: with
   a preview showing, advancing 16s re-fetches; a response with one more turn
   makes the next fetch land 1s later; unchanged responses then stretch the gap
   back out to 16s and stay there. `view.preview.turns` reflects the new
   response and `selected` never changes.
3. `refreshSessions()` with a preview showing re-fetches the preview; today it
   does not, so this is the assertion that pins the Refresh-button half.
4. A `visibilitychange`/`focus` event in jsdom triggers a refresh, and one that
   finds a change resets the delay to 1s.
5. No poll fires while the tab is hidden, after attach, after switching away, or
   after `dispose`; and a fetch that resolves *after* the user attached does not
   put `view.preview` back.

**Fixed** in 2087ca5: `controller.refreshPreview()` re-reads the previewed
transcript and replaces `turns` without touching `selected`, driven by a chained
`setTimeout` in `controller.ts` whose delay comes from the pure
`nextPreviewDelay` in the new `src/client/preview-poll.ts` — 16s idle, 1s on a
change, doubling back to a 16s ceiling on each quiet *tick* only. `App.svelte`
owns the `visibilitychange`/`focus` listeners and `main.ts` injects
`() => document.visibilityState !== "hidden"`, so `controller.ts` still contains
no `window` or `document`. `refreshSessions()` now calls the refresh too, which
covers both the Refresh button and `sessions-changed`. `refetchPreview`
*captures* `selectionIntent` rather than bumping it — bumping would silently
cancel a click whose own preview or attach is still in flight, which is its own
test. All five "Done when" assertions are covered by 11 new tests (3 in
