# No way to mark sessions the reader cares about, so a long list has no durable ordering cue beyond recency.

The agreed shape, deliberately minimal: a per-viewer **star** toggled from each
list row, persisted **client-side in `localStorage`** (key e.g.
`agentpane:stars`) as a `Set` of `sessionKey(ref)` strings, so it survives
reload -- unlike the workspace/backend/reading selects, which are session-only
`$state` by design. Render starred rows distinctly; whether to float them to the
top of the list is a choice to make in-flight. **Two hard constraints, both
settled with the owner.** (1) **No star on a virtual session.** A session
renames on its first prompt (D9: `virtual:…` -> real backend id), so a key
placed before that would strand; forbidding the star until the session is
materialised (`status !== "virtual"`) sidesteps the migration entirely. The
`controller.onRename` hook that App.svelte already uses to re-key its
scroll/follow maps is the escape hatch if that limit ever proves too strict --
name it, do not build it. (2) This would be agentpane's **first browser-local
persistence** -- a real posture change, chosen because a star is a per-viewer
view preference, not a fact the server owns; it keeps the server stateless.
**Why this is a deferral, not scheduled:** the store is the open question. If
agentpane grows client- or server-side state for another reason before this is
built, that decision should set where stars live (a per-viewer `localStorage`
set, or a server-owned sidecar keyed by ref if stars ever need to travel between
browsers) rather than this row pre-committing it. Revisit when that state
question resolves or the list gets long enough to hurt. Done when: a test with a
real/mock `localStorage` shows a toggled star persists across a simulated
reload, is keyed by `sessionKey(ref)`, and that a virtual session exposes no
star control.
