# The model list is empty with nothing attached, and that is accepted: a session is created with the default model and changed after attach.

**Decided by the owner on 2026-08-19: accept it, and build the picker (if ever)
against the route as it stands.** Two reasons, and the second is the stronger.

The gap is narrower than the route's own comment implies. `controller.select`
goes straight to `attachAndSelect` (`controller.ts:411`) -- selecting a session
attaches it, and preview is a separate read-only path -- and a new session
inherits its workspace and backend from the *selected* session. So at the
moment a picker would be opened to make another conversation like this one,
there is normally a live adapter of that backend and the route answers
authoritatively. What is left is cold start with nothing selected, and whatever
D12's reaper or LRU cap has evicted.

And the choice barely exists. The owner's actual model selection at work is
**Pi means Opus 4.8 and Codex means GPT-5.4** (stated 2026-08-19) -- the
backend *is* the model choice, so a picker may never earn its keep at all.
Weigh that before building one, rather than treating the picker as given and
this item as the only obstacle.

## What was ruled out, so it is not re-proposed

**A backend-level model source.** Neither backend has one. Codex's
`listModels` opens with `requireClient()` (`codex/adapter.ts:465`) and then
issues `model/list` over JSON-RPC; Pi's issues `get_available_models` over
stdio (`pi/process.ts:415-418`). Both answer only from a running subprocess --
the route's comment records the limitation as verified against `PiAdapter`, but
the mechanism is identical on both sides, so with nothing attached the route
returns an empty list for *both* backends, not just Pi. A session-independent
source would therefore mean parsing config files: a second source of truth that
drifts from what the agent will actually accept, discovered only when
`setModel` fails.

**Spawning to answer a listing question**, which D9 rules out and the route's
own comment already cites.

## If it does bite, the answer is already determined

Cache the last live answer -- write a per-backend list whenever a live
`listModels()` succeeds, read it when nothing is attached. It never spawns, so
D9 is satisfied. Do not design storage for it: D13 gives the server its first
owned store under OW-66, with an injectable directory and temp-file-plus-
rename writes, and this is a small addition to that rather than a new
mechanism. So this waits on OW-66 for free rather than waiting on a decision.

## One thing to fix whenever a picker is built

The route swallows both failure modes with bare `catch` blocks -- `app.ts:336`
for a factory that will not construct, `:343` for a backend that cannot
enumerate. A client therefore cannot tell "this backend offers no models" from
"nobody could ask", which is exactly the distinction an empty dropdown needs to
explain itself.
