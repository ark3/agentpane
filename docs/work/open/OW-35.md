# Prompting a detached/reaped session must transparently attach-then-submit, so D12 eviction is invisible.

`src/client/controller.ts`

When idle/LRU (OW-33/34) has reaped a session's subprocess, a prompt to it must re-attach before submitting rather than fail.
Verify the controller's current behavior first.
Since OW-tewave landed on 2026-09-16 the client does call the `DELETE` route, from a Detach item in the composer's Tools menu.
That does **not** make this card's scenario reachable, which OW-tewave's own text got wrong and OW-jamoyi corrects: after a detach the preview loads, `previewing` goes true, and `src/client/App.svelte` replaces the whole composer with a single Attach button, so there is no prompt box from which to prompt a detached session.
The path from that screen is `api.attach`, not attach-then-submit.
The one way the normal flow arrives here is a *failed* preview, which leaves `view.preview` null and the composer drawn over a session the client has dropped -- an error path, not the scenario.
So this card still waits on the reaper (OW-33/34), or on a second client detaching a session out from under this one (OW-fihuma's case), and it is still only the re-attach path, not any button removal.
Constraint for the D12 implementer: keep the `DELETE` route — it is programmatically useful and shutdown-adjacent code relies on it.

## The resume beneath this card works, observed 2026-09-16

Watched live on the home server against `pi 0.85.1`, driven at the HTTP routes: create, attach, one prompt, `DELETE`, attach again, second prompt (OW-jamoyi, recorded in `docs/MANUAL_TESTING.md` under "`DELETE` then attach resumes a real Pi session, and the resumed spawn drops the model").
No browser was open and the Attach button was never pressed, so the resume is proven at the routes and the UI path this card's repair would run through is still unobserved.

Both halves of the resume hold.
The re-attach's first snapshot carried turn 1's messages, identical to the pre-`DELETE` snapshot in `timestamp`, `usage` and `responseId`, and they can only have come off Pi's JSONL: `close()` disposes the adapter holding the reducer state, so nothing in the server survives to replay them.
The claim that matters is the second one, since `--session <resumeId>` exists for it: the second turn ran on a process spawned after the kill was confirmed dead by pid, and it answered facts planted in turn 1, which it could have read nowhere but the resumed file.
Its usage corroborates rather than proves -- `input: 89`, `cacheRead: 1536`, `cacheWrite: 0`, where `input: 89` is far too small to have carried turn 1 itself.
So `--session <resumeId>` genuinely rehydrates, and the attach-then-submit this card asks for has a working resume underneath it.
Both turns appended to one session file, parent-linked across the detach.

Two things the D12 implementer inherits from that run.
The resumed spawn carries `--session` and **no** `--model`, because `close()` drops the session from the manager's table and `#start`'s `!session` branch rebuilds it with no model field -- so a reaped-then-reprompted session may not come back on the model the user chose; that is OW-pubulu, and the reaper is what turns it from obscure into the common path.
And Pi materialises its session file at *attach*, not at its first prompt, so a reaped session's id is already its final one and the re-attach is not a rename point.
That is not new -- `docs/HANDOFF.md` finding 41 measured it on `pi 0.84.1` and warned that code written for only the prompt-time rename will miss it -- but roughly 23 places in the repo still assert the first-prompt version, D9 among them; that reconciliation is OW-bohodu.
