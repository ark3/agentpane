# Whether to build the `ow` tool at all, and which of its subcommands earn their keep — deliberately not decided until OW-54's storage has been lived with.

Split from OW-54 on 2026-08-16: format and tooling choose independently, and
bundling them meant judging what to automate before there was any experience of
the storage to judge from. The four sketched subcommands (`new`, `close`,
`list`, `check`) are a guess at the surface, and this project's habit is to take
a rough cut and get a verdict from using it, which this row exists to make
possible. The third option this row used to carry — take beads' CLI instead of
writing one — is **gone as of 2026-08-17**: beads was ruled out with OW-54, so
nothing now couples the format and tooling axes and this row can only be built
or declined, not dissolved. **Blocked on OW-54 landing, and then on running
without the tool long enough to say which absence actually hurt.** The interim
cost is smaller than this row first claimed and is now measured: a two-line
`rg`+`sort -V` survey prints every open row as kind-plus-headline, simulated
from the real corpus at ~7KB for 42 rows on 2026-08-17 (against 60KB to open the
table; an earlier "measured at ~4.3KB" here was an extrapolation from synthetic
rows, corrected under OW-69), so there *is* a single view and `ow list` would
buy formatting and a memorable name rather than a missing capability
(`TRACKING.md`, "Tooling"). The committed-index alternative this row used to
offer is ruled out by TRACKING finding 2. **The specific thing to watch during
the interim**, named by the owner on 2026-08-17: `/execute` invoked with no id
is asked "what is on deck, what do you recommend", and `/author` needs to spot a
redundant row before filing one. Redundancy and reverse-dependency lookups both
improve outright under the format (`rg -l` returns one path per matching row
instead of the whole 400-word line, and the id is read off the path). The survey
is the case that might not — record whether kind-plus-headline was enough to
recommend a next row, or whether it always meant opening three or four files
anyway. **New requirement, from the owner on 2026-08-17: the tool should work in
other projects too**, which is a real constraint on its design and not a
nice-to-have — it is also the whole of what he meant by wanting to move off the
`OW-` prefix. So the tool must not hardcode a prefix; derive it from the
filenames already present, or read it from a per-project setting. Then agentpane
keeps `OW-` at zero cost and another project picks its own. `docs/TRACKING.md`'s
prefix section carries the measurement behind not renaming (80 of 172 commit
subjects name an `OW-` id, and the repo is now pushed). Nothing in OW-54 needs
changing for this: the id *is* the filename, no frontmatter field repeats it,
and none of the survey commands mention the prefix — but do not let the
migration introduce a new place it is baked in. Done when each subcommand is
either written or recorded as not wanted, with the reason being something
observed during that interim rather than predicted here.

**First observed interim cost, 2026-08-18: `new` earns its keep, and for a
reason this item did not predict.** Hand-allocation is not merely inconvenient,
it is unsafe under concurrent sessions in one clone — an authoring session read
the max id as 69, another session filed OW-70 and OW-71 into the same working
tree half an hour later (`1e40fc4`), and the first overwrote both (`5addf08`)
with no signal from git at all. `docs/TRACKING.md`, "Two clones can mint the
same id", now records the case and the interim remedy (a non-clobbering write,
and re-reading the max id in the same command that writes). That remedy is a
rule an agent must remember; `ow new` would make it structural by allocating and
creating in one step. Weigh that against the same-project-only concern above: an
allocator that is wrong about which directory it is reading is no safer, so
whatever `new` does has to read the live directory at write time rather than
trust anything cached.

**Superseded the same day: `new` shrinks to nothing, and `check` takes its
place as the subcommand with a concrete argument.** The id scheme changed on
2026-08-18 (`docs/TRACKING.md`, "Ids are drawn at random"), and the paragraph
above justified `new` by a safety property the scheme now provides for free —
there is no allocation left to make atomic, and drawing a name is one line of
`python3` that `author/SKILL.md` carries inline. What `new` would still buy is
the skeleton and a memorable name, which is the same small thing `list` buys,
so it goes back to waiting for evidence with the rest. `check` moves the other
way. A citation typo used to be `OW-77` for `OW-76`, catchable by eye against
the id range; `OW-kerata` for `OW-keraha` is not, and the only thing that finds
it is `rg 'OW-[a-z-]+'` cross-referenced against the filenames in both
directories. Of the four invariants sketched in TRACKING's "Tooling", that is
the one the scheme change made harder rather than easier.

## What living without the tool actually showed, 2026-08-19

The interim this item was waiting on has now produced evidence, gathered in a
triage session that read every open item. Recorded per subcommand, because the
item's own closing condition asks for exactly that.

**`check`: both invariants ran by hand, and both are mis-specified.** Reproduce
with a short `python3` script -- collect `OW-[0-9]+|OW-[a-z]+` matches across
`docs/`, `src/`, `e2e/` and the root markdown, and diff against the stems in
`docs/work/{open,closed}/`; then, separately, pull the sha out of each closed
item's `**Fixed** in` line and `git cat-file -t` it.

*Every cited id exists* produced four hits and **four false positives**.
`OW-007` is `TRACKING.md`'s own zero-padding example, which that document
already flags at `:111` as the one unmatched string. `OW-77`, `OW-keraha` and
`OW-kerata` are the illustrations **inside this item and TRACKING** of the
typo the check exists to catch. So the noise comes from the documents that
describe the invariant, and a naive implementation cries wolf on 100% of its
output. It needs a way to tell a citation from an example.

*Every closed item carries a real sha* produced one violation, and it is
legitimate: OW-74 was closed unbuilt, and its own text says "This is the first
close in the corpus that is not a `**Fixed** in <sha>`". The invariant as
written in TRACKING's "Tooling" is therefore already wrong about the corpus --
there are two legitimate close shapes and it knows about one.

**`list`: the survey was enough to triage and could not have been enough to
decide.** That session was precisely the `/execute`-with-no-id case this item
named as the thing to watch. The two-line survey printed all 41 open items as
kind-plus-headline and sorted them into decision / evidence / defect without
trouble. What it could not do was ground a recommendation: eleven item files
were opened in full and source was read for every one, and **four of the
eleven turned out to have already answered themselves** -- visible only from
the code, never from any rendering of the item text. So `list` buys formatting
and a name, as predicted, and formatting was not the bottleneck.

## The owner's corrections to the above, same day

**`new` was undersold, here and in the paragraph above that retired it.** The
claim that the draw is "one line of `python3`" describes one third of the
procedure. `author/SKILL.md:38-51` mandates draw, **check the candidate against
both `open/` and `closed/`**, then **create the file exclusively**
(`set -o noclobber` or `cp -n`) -- and in practice an agent draws several
candidates at once, checks them in a second call, then writes, because a
collision means starting over. `ow new` collapses that into one step that
cannot be half-done. That is the same argument that favours `check`
-- structural rather than remembered -- and this item had been applying it to
one and not the other.

**`list`'s value is queries, not rendering.** By kind, by dependency, and
"what is unblocked" are things the raw survey cannot express at any formatting
quality, which is a different proposition from the one the evidence above
tested.

**That reopens a format question, not a tooling one.** Dependency edges do not
exist in the data: frontmatter carries `kind` and `where` and nothing else, and
every blocking relation in the corpus is prose -- this item's own "blocked on
OW-54 landing", OW-vezipo's "waits on OW-66 landing", OW-21's deferral to
D13's store. Nothing can query any of them. `ow list --unblocked` therefore
needs a `blocked-by:` frontmatter field first, which is `docs/TRACKING.md`'s
decision to make, not this item's. Worth noticing that TRACKING records the
*old* table's revisit condition as "if the list starts wanting fields this
table cannot carry -- **dependency edges between rows**, or who holds what".
That condition never fired for the table; it is firing now, one format later.

**`close` is a modest but real win**: two tool calls to one, plus resolving
`HEAD` to a sha only knowable after committing, plus two close shapes to get
right rather than one.

## Two more subcommands weighed, 2026-08-20

**`show <id>` was proposed by the owner, after a live failure.** A Codex session
closing OW-yudoni was pointed at OW-hezidi by id, built
`docs/work/open/OW-hezidi.md` from the one path shape AGENTS.md stated, found
that the item had closed, and reported it missing. Two things weaken it as an
argument for tooling: `cat docs/work/*/<id>.md` already resolves either
directory, so the capability is not missing but merely unnamed, which puts
`show` in the `list` pile above rather than the `check` pile; and the sentence
that misled it has since been fixed (AGENTS.md, "Landing work", `0ee6dd9`), so
the defect has a remedy on trial. What survives is that this is the first cost
observed for a subcommand this item never sketched, that it came from a
different model reading the same docs — evidence about how resolvable the
convention is to a cold agent, not about one agent's care — and that `show` is
where the cross-project requirement actually bites, since the glob hardcodes
`docs/work/` while every other verb can be told a path once. Recorded rather
than decided: **if id resolution fails again now that the doc names both
directories, that is the argument.** Today's is not.

**`list` gained a second argument, and it is stronger than the formatting one:
filtering on things the corpus already knows.** Owner, 2026-08-20, naming two
dimensions — dependency edges and resource gating. They are not in the same
state. Dependency needs `blocked-by:` to exist first and is TRACKING's call, as
recorded above. **Resource gating needs no format change at all**, which is what
separates it: the `**Work laptop:**` marker is mandated by AGENTS.md and carried
by 5 of the 40 open items today. The problem is that the two views cannot be
combined. The survey prints kind-plus-headline for all forty and never shows the
marker; AGENTS.md's `rg -l '^\*\*Work laptop:\*\*'` returns those five as bare
paths and never shows what they are. So "what is open and doable on the machine
I am sitting at" is an intersection done by eye, in both directions: on the home
server it is five items to exclude before triage starts, and at the laptop it is
precisely the batch that AGENTS.md's one-visit rule wants seen as a set before
the trip. That is a missing capability rather than a nicer rendering of an
existing one, which is the distinction this item has been sorting subcommands
by.

## Still open, deliberately

The owner was not ready to decide on 2026-08-19. The shape of the remaining
decision, for whoever picks this up: `check` is the only subcommand that looks
for a defect nobody is looking for, which argues for it running automatically
rather than being typed -- the repo precedent is
`src/import-boundaries.test.ts`, which fails the build and names your file, and
`vite.config.ts`'s server project already globs `src/*.test.ts`. But automatic
means repo-local, and that pulls directly against the **cross-project
requirement** recorded above. Whatever is built has to answer that tension
rather than pick a side by accident. And both `check` invariants need
respecifying against the two findings above before either is worth automating.

## The work context flipped the verdict, and a tool is being built, 2026-08-20

The owner intends to run this workflow at work — corporate Jira as the public
record, shared repos, no managing of agents in public — and that context
settles the question this item kept deferring, from outside the interim that
was supposed to settle it. There the corpus cannot live in the project repo,
so something has to resolve where it does live, and that something is the
tool: **location abstraction is a missing capability, not a nicer rendering of
an existing one**, which by this item's own sorting criterion moves the tool
from "waits for evidence" to load-bearing. Same subcommands, opposite verdict,
purely because the context changed what they provide. The decision: build a
minimal `ow` — corpus resolution, `new`, `close`, `exec`, `worktree` — in its
own repository, seeded as `~/projects/openwork` on the home server with a
design brief (`BRIEF.md`) recording the two-tier Jira model, the verb
inventory, and the evidence each verb carries out of this item. Agentpane is a
consumer of that tool, not its home, which is the cross-project requirement
above reaching its natural conclusion.

Two verbs this item never sketched, both surfaced in that discussion. **`exec
-- <cmd>`** runs an arbitrary command in the corpus directory: the escape
hatch that keeps TRACKING's "Staying greppable" constraints load-bearing after
the tool arrives, because the format stays the API and the tool stays a
resolver plus verbs rather than the owner of a query language. **`worktree`**
does the mechanical setup `execute/SKILL.md:37-42` carries as remembered
prompt procedure — cut the worktree, `git merge --ff-only main`, report the
starting sha, run the project's install, probe the sandbox — which is the
structural-rather-than-remembered argument applied to a procedure that lives
in a prompt today.

Two demotions, recorded so the work-context evidence cuts both ways. `list`
loses its strongest argument there: the owner's corpora at work are
ticket-scoped — fanned in from a Jira ticket, worked, then promoted or
declined to zero open items — so the backlog queries that earned `list` above
(by kind, unblocked, resource gating over 40 items of mixed age) have nothing
to query. And everything Jira-shaped stays unbuilt for this item's own reason:
no usage has named those verbs yet. `check` remains where the previous section
left it — both invariants need respecifying first, and the
automatic-versus-portable tension is now sharper, not resolved, since the tool
is definitely cross-project.

What this means for closing: the subcommand outcomes this item's done-when
clause asks for will now land as commits in the openwork repository, so the
eventual close note here may cite evidence outside this repo. OW-74 already
established that a close is not always a `**Fixed** in <sha>`; this would be
the first whose evidence lives in another repository. Not closed today because
nothing is built yet — the verbs above are decided, not written.
