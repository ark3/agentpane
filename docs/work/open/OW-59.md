# Whether to build the `ow` tool at all, and which of its subcommands earn their keep — deliberately not decided until OW-54's storage has been lived with.

Split from OW-54 on 2026-08-16: format and tooling choose independently, and
bundling them meant judging what to automate before there was any experience of
the storage to judge from. The four sketched subcommands (`new`, `close`,
`list`, `check`) are a guess at the surface, and this project's habit is to take
a rough cut and get a verdict from using it, which this row exists to make
possible. The third option this row used to carry — take beads' CLI instead of
writing one — is **gone as of 2026-08-17**: beads was ruled out with OW-54, so
nothing now couples the format and tooling axes and this row can only be built
or declined, not dissolved. **Blocked on OW-54 landing, and then on running
without the tool long enough to say which absence actually hurt.** The interim
cost is smaller than this row first claimed and is now measured: a two-line
`rg`+`sort -V` survey prints every open row as kind-plus-headline, simulated
from the real corpus at ~7KB for 42 rows on 2026-08-17 (against 60KB to open the
table; an earlier "measured at ~4.3KB" here was an extrapolation from synthetic
rows, corrected under OW-69), so there *is* a single view and `ow list` would
buy formatting and a memorable name rather than a missing capability
(`TRACKING.md`, "Tooling"). The committed-index alternative this row used to
offer is ruled out by TRACKING finding 2. **The specific thing to watch during
the interim**, named by the owner on 2026-08-17: `/execute` invoked with no id
is asked "what is on deck, what do you recommend", and `/author` needs to spot a
redundant row before filing one. Redundancy and reverse-dependency lookups both
improve outright under the format (`rg -l` returns one path per matching row
instead of the whole 400-word line, and the id is read off the path). The survey
is the case that might not — record whether kind-plus-headline was enough to
recommend a next row, or whether it always meant opening three or four files
anyway. **New requirement, from the owner on 2026-08-17: the tool should work in
other projects too**, which is a real constraint on its design and not a
nice-to-have — it is also the whole of what he meant by wanting to move off the
`OW-` prefix. So the tool must not hardcode a prefix; derive it from the
filenames already present, or read it from a per-project setting. Then agentpane
keeps `OW-` at zero cost and another project picks its own. `docs/TRACKING.md`'s
prefix section carries the measurement behind not renaming (80 of 172 commit
subjects name an `OW-` id, and the repo is now pushed). Nothing in OW-54 needs
changing for this: the id *is* the filename, no frontmatter field repeats it,
and none of the survey commands mention the prefix — but do not let the
migration introduce a new place it is baked in. Done when each subcommand is
either written or recorded as not wanted, with the reason being something
observed during that interim rather than predicted here.

**First observed interim cost, 2026-08-18: `new` earns its keep, and for a
reason this item did not predict.** Hand-allocation is not merely inconvenient,
it is unsafe under concurrent sessions in one clone — an authoring session read
the max id as 69, another session filed OW-70 and OW-71 into the same working
tree half an hour later (`1e40fc4`), and the first overwrote both (`5addf08`)
with no signal from git at all. `docs/TRACKING.md`, "Two clones can mint the
same id", now records the case and the interim remedy (a non-clobbering write,
and re-reading the max id in the same command that writes). That remedy is a
rule an agent must remember; `ow new` would make it structural by allocating and
creating in one step. Weigh that against the same-project-only concern above: an
allocator that is wrong about which directory it is reading is no safer, so
whatever `new` does has to read the live directory at write time rather than
trust anything cached.

**Superseded the same day: `new` shrinks to nothing, and `check` takes its
place as the subcommand with a concrete argument.** The id scheme changed on
2026-08-18 (`docs/TRACKING.md`, "Ids are drawn at random"), and the paragraph
above justified `new` by a safety property the scheme now provides for free —
there is no allocation left to make atomic, and drawing a name is one line of
`python3` that `author/SKILL.md` carries inline. What `new` would still buy is
the skeleton and a memorable name, which is the same small thing `list` buys,
so it goes back to waiting for evidence with the rest. `check` moves the other
way. A citation typo used to be `OW-77` for `OW-76`, catchable by eye against
the id range; `OW-kerata` for `OW-keraha` is not, and the only thing that finds
it is `rg 'OW-[a-z-]+'` cross-referenced against the filenames in both
directories. Of the four invariants sketched in TRACKING's "Tooling", that is
the one the scheme change made harder rather than easier.
