# Whether a Codex `plan` item deserves bespoke rendering or stays assistant text, which nothing can judge until a capture exists.

Half of this settled without being asked. `contextCompaction` got bespoke
rendering under OW-72 (`e22740d`) -- a marker drawn by one component for both
backends -- so only `plan` is still open. See OW-6's close note for that half.

`plan` currently folds into assistant text: `mapping.ts:339-345` returns
`assistant(ctx, textBlocks(item.text), ...)`, and its comment states the
position rather than hiding it -- DESIGN leaves plan rendering open ("assistant
text or a custom block") and "Text is the honest minimum: it is literally a
text field." It streams like an agent message, via `item/plan/delta` appending
to `item.text` (`reducer.ts:217-222`), so anything bespoke has to render
partial text too.

**The blocker is that nobody has seen one.** There is no `plan` in any fixture
(`resources/fixtures/{codex,pi}/` hold `text`, `tool-read`, `tool-edit`,
`compact` and `fork`), and `DESIGN.md:653` still lists it among the rows with
no capture. Whether a custom block buys anything depends entirely on what the
text turns out to be -- a checklist worth structuring, or a paragraph that
markdown already renders correctly. Deciding first and capturing second would
be guessing at the answer and then finding evidence for it.

## Revisit when

A `plan` capture exists under `resources/fixtures/codex/`, added by a scenario
in `resources/probes/capture_fixtures.py` the way OW-72 added `compact`. That
is a work-laptop job, since it needs a live Codex turn that produces a plan.
Closing this means looking at the captured text and either building the block
or recording that text was right -- not a UI tweak made in passing.
