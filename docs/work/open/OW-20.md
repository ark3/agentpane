# What observation should trigger building an index cache for session listing, given the current answer is a recorded "not yet" rather than an open question.

The stance is already in the code and is not drifting: `sessions/index.ts:1-10`
says "No cache -- fresh walk + read on every call", cites D9 and the measured
numbers (973 files across 28 workspaces, ~0.3s in Python), and notes the module
"leaves room for one (a cache would slot in here, in front of `findJsonlFiles`
+ the per-file parsers) without being one". `line-reader.ts:12-20` is built
around the same decision: bounded, breakable reads so enumeration stays cheap
rather than being compensated for later.

So this item is not undecided, it is **waiting** -- and what it is waiting for
is the loose part. "Once the corpus is larger than ~973 sessions" is the wrong
trigger. The walk is readdir-only and the per-file reads are bounded and
abandoned early, so cost scales with file count in a way that a bigger corpus
alone does not settle; a listing that got slow because one store grew
pathological files is a different problem with a different fix. The trigger
should be a **measured listing latency** on the real corpus, taken the way
HANDOFF 19 took the original.

"Both upstreams eventually built one" stays as the reason to expect this to
fire eventually, not as evidence that it should fire now.

## Revisit when

`GET /api/sessions` is measured slow enough to notice in the client on the
owner's real corpus. Record the number where D9's numbers live, then decide.
Closing this without a measurement -- in either direction -- is the outcome to
avoid.
