# D35. A live session answers to one name, a start has a deadline, and a close names a handle

The owner took this on 2026-11-21 (ark3/agentpane#27), on the census written into that issue's body the same day.
**Partly built**: point 2 landed with ark3/agentpane#87 on 2026-11-21; ark3/agentpane#88 to #90 carry the rest, under "Issues" below.

**What stood.**
`SessionManager` in `src/server/http/session-manager.ts` held a live session under every name it had had, and a startup under every name it answered to, so that a close by ref could reach it from any of them.
D24 built that in three rounds of name-keyed records (OW-bulanu, OW-yufazo, OW-kamave), each review finding the next case, and two edges were still open (OW-giyimu, OW-loromi).
The census found most of it to be copies of one another, or defences against orders that only several names or a close reaching a startup could produce.
Since D31 point 9 every command on a live session names a handle, so a ref enters the manager only at an attach, a prompt by ref, a preview, a listing and a close; and the manager itself carried refs across its own awaits, from `create` and `attachAndSubmit` to `forkAndPrompt`.
What put several names on one container was a rename inside `start()`, whose old name no client holds; Pi's rename at a first prompt, which `pi 0.87.1` and `1.2.0` did not make; Claude Code's `init` naming another id, never seen; and Pi path spellings, which differ only through a symlinked store, on neither machine (owner, 2026-11-21).
No client closes a startup of its own: the browser offers Detach only on a row its listing shows attached or virtual, and agentpane-mode refuses a close from a buffer that is not attached (`agentpane-close-session`).
And the server had no deadline on a start, so a close was the only thing that stopped one that hung.

**The decision.**

1. **A live session answers to one name, its current ref.**
   `#names` maps each container's current ref to its handle and holds nothing else, and a rename moves the entry.
   An id the session has outgrown reaches nothing: an attach or a prompt by it goes to the index, which finds the conversation's file if it has one and answers `not_found` if not.
   A stored session attached under a spelling the index canonicalises is found by the canonical ref the lookup names, as before, and the spelling becomes no name.
   `attach` answers the container it landed on, so `create`, `attachAndSubmit`, `forkAndPrompt` and the socket's `sessions/attach` read the session from that answer instead of looking a ref up again, and `list()` has no outgrown names to hide.
   Accepted: a listing row read before a rename and clicked before the `sessions-changed` that rename sends answers `not_found`.
   The build pins that attaching a stored Pi session makes no rename, since one that did would list that session twice.
2. **A start has a deadline.**
   `startTimeoutMs`, a named constant beside `maxSessions`, is 60s, a first cut with no start times measured, run on the injectable `AppDeps.setTimer`.
   A start that has not resolved by then fails with a new refusal code, `start_timeout`, through the ordinary failure path: its adapter killed and nothing left.
   It bounds every start, an attach's, a create's, a prompt by ref's and a fork's attach.
   Each client shows the refusal's detail as it shows any other.
   agentpane-mode's `agentpane--spawn-timeout` goes from 60s to 90s, so that the server's answer reaches it first.
3. **A close names a handle.**
   `sessions/close` takes `{ handle }` like every other command on a live session, and is refused `not_attached` where that handle has ended, which settles what D31 point 9 left to ark3/agentpane#27.
   So a close never reaches a startup, which ends by publishing, failing, timing out or the server's shutdown, and a second close of one handle is refused rather than resolving before the first's disposal (OW-loromi).
   The browser's `detach()` sends the handle of the selected view, and `detachable` in `src/client/App.svelte` drops its `virtual` clause, since a virtual row has been a create mid-start since D30.
   The Emacs helper's `sessions/close` sends the handle the view is bound to, and refuses `not_attached` from a view bound to none, as it refuses every other request on a live session.
   D12's reaper and cap close the container they hold, not a ref.
4. **Every disposal is waited out under one ref.**
   `#disposing` holds one entry per disposal, under the ref of the conversation being disposed: a close's under the closed container's ref, and a failed or timed-out start's reaping under the ref it was started for.
   An attach, or a prompt by ref, that names that ref, or whose index lookup names it, waits it out and then starts afresh, so no two adapters ever share a file (D32 point 5).
   Nothing joins a failed start: an attach that joined it before it failed fails with it, and one that arrives during the reaping waits that out.
5. **Startups are a set, not an index.**
   The manager keeps its startups in a plain set, for `disposeAll` to reap and `#makeRoom` to count, and a container carries the startup that is building it, for an attach to join.
   Two attaches of one stored session collapse at the arbitration after the index lookup, where the claim is synchronous, so the second finds the first's container.
   Shutdown is the only teardown that reaches a startup, so `#shuttingDown` replaces `PendingStart.torndown`.
6. **A fork whose start fails leaves nothing, as a create does.**
   `forkAndPrompt` hands the recipe, or the Codex fork's adapter, to the fork's start itself, and parks nothing.
   Its refusal then names no fork, and each client stays on the parent with the edit open and its text kept, which is D30's path where none is named; neither client changes.
   A Codex fork's file, written before the start that failed, is left on disk, an orphan D17 accepts.
   A Pi fork that fails after it moved, and a fork whose prompt is refused after its attach, still name the fork live.
   Leaving the edited message behind on the server would be better, and is deferred until it is needed in use (owner, 2026-11-21).

**What stays.**
- The handle as the key, minted with the manager's random prefix (D24).
- The arbitration after the index lookup, and its claim with no await before it.
- `PendingStart`'s adapter and its one disposal (`#terminate`), since teardown and the failure path can both reach an adapter mid-start.
- The wait out of a close's disposal before an attach starts again (D32 point 5).
- `#rename`'s hold of a rename inside `start()` off the wire until the publish.
- D12's clocks and exemptions, on the container.

**The census's doubts.**
- Whether anything still reached the ref a failed start restored onto its container: nothing needs to, since point 4 registers the reaping under the ref it was started for and the container goes.
- Whether the virtual container `create` puts in the table before its adapter is needed: it stays, as the container whose startup point 5 joins, and it is what `holds()` finds for a create mid-start.
- Whether parked forks were an order or a policy: point 6 takes them as policy and drops them.
- Census item 32 read agentpane-mode as closing a buffer whose attach is out; it does not, since it refuses a close from any buffer not attached.

**What it amends.**
- **D9:** a rename is no longer one more name on the container, and an id a session has outgrown stops resolving to it.
- **D12:** the cap counts the set of startups, and the reaper and the cap close the container they hold; the bookkeeping constraint's reach "through `#lookup` from any of its names" goes.
- **D24:** the container's names, OW-kamave's `PendingStart.keys` and `#attaching`, `#handOver`'s hand-over of spellings and the join of a failed start's reaping, `#pendingForks`, and "whether the manager holds a ref", which becomes a container in the table under it. OW-giyimu and OW-loromi are settled here.
- **D25 point 1:** the close carries its handle too.
- **D26 point 1:** a close always finds a container, since it names a handle. **Point 5:** no parked fork is held.
- **D30:** a fork whose own start fails leaves nothing and is not named, and `ForkNotPromptedError` names a fork only once its attach has published.
- **D31 point 9:** the close names its handle.

**What it deletes.**
Measured against ark3/agentpane#67's baseline at 93e24d4d, where `src/server/http/session-manager.ts` was 1,731 lines and its test file 3,776; at 1f3d4f65 they were 1,870 and 4,077, ark3/agentpane#31 having added most of the difference.
- Whole forms in the manager, about 150 lines at 1f3d4f65 with their docstrings: `#addName`, `#hold`, `#holdKey`, `#bind`, `#handOver`, `#afterDisposal`, the `PendingFork` type, the `#pendingForks` and `#attaching` fields, and `ManagedSession.names`.
  The reads by ref, `isAttached`, `adapterFor`, `liveRefs` and `canonicalRef`, stay: under one name they read the current ref, and the tests use them well beyond this state.
- `#start` (238 lines), `close` (118), `attach` (63), `forkAndPrompt` (57), `disposeAll` (55), `PendingStart` (34) and `#retire` (19) shrink by perhaps another 300: an estimate, not measured.
- The timeout, its refusal and the disposal registration of point 4 add perhaps 40.
- So the manager would come to about 1,460 lines, some 270 below the baseline.
- In the test file, 52 tests over about 1,500 lines pin the aliases, the spellings, a close's reach into startups, joins into a failed start and parked forks; some come back as tests of points 2 to 6, so the file would shrink by perhaps 1,200 lines.
- Outside the manager, little moves: `sessions/close`'s params in `src/shared/protocol.ts`, its handler in `src/server/http/socket.ts`, `close` in `src/client/api.ts`, `detach()` and `detachable`, the helper's `sessions/close`, and the probes and test stubs that close by ref.
- A grep can check it: once built, `rg -n '#attaching|#pendingForks|#handOver|#afterDisposal|#holdKey|#addName|PendingFork\b|torndown' src/server` finds nothing.

**Issues.**

2. ark3/agentpane#88, point 3: the close by handle on both wires, the reaper and the cap closing their container, and the deletion of a close's reach into startups.
3. ark3/agentpane#89, point 6: a fork's failed start leaving nothing, and `#pendingForks` going. After #88.
4. ark3/agentpane#90, points 1, 4 and 5: one name per container, the disposal registry under one ref, and startups as a set. The largest, after #88 and #89; a cold read should precede it.
