# D33. agentpane-mode forks only by an edit, as the browser does, and marks the messages it can fork at

The owner took this on 2026-11-21 (ark3/agentpane#17), on a proposal the coordinating session made once D32 was built.
**Decided; points 1 to 3 built by ark3/agentpane#75, point 4 not yet built** (ark3/agentpane#76).

**What stood.**
In the browser a fork is an edit: an earlier user message goes back into the composer, and sending forks the session at that message and prompts the fork, as one `sessions/forkAndPrompt` (D30).
agentpane-mode had that too, as `e` and `C-c C-e` (`agentpane-edit`, `agentpane-edit-last`), and also `f` (`agentpane-fork`, OW-fojike), which forked at the message at point and opened the fork with nothing sent, over the plain `sessions/fork`.
The owner decided on 2026-11-01 that the browser's fork is the right model.
The plain fork was the last holder of a per-buffer "fork in flight" flag (`agentpane--forking`), and, since D32 point 6, of the `unwatch` bit on `sessions/abort` and `sessions/fork`.
The browser marks the messages it can fork at with its ✎, from the fork points it holds for the session on screen (`refreshForkPoints` in `src/client/controller.ts`), refreshed at attach and at each turn boundary; agentpane-mode marked nothing and said a message was not forkable only when a key was pressed (OW-wozoju).

**The decision.**

1. **`f` starts the edit.**
   `f` on a user message does what `e` does: it takes the message into the prompt region as an edit, and sending forks at it and prompts the fork.
   `e` stays bound to the same command, and `C-c C-e` still edits the last user message.
   The fork that opens with nothing sent goes, and so does `agentpane-fork`.
2. **The fork opens where the edit's send opens it today.**
   It opens in a transcript buffer of its own, shown in the window that showed the parent at the send (`agentpane--show-fork`), as the browser moves its selection to the fork.
   The parent's buffer keeps its session.
3. **The plain fork goes from both wires.**
   `sessions/fork` goes from the socket's commands in `src/shared/protocol.ts` and from the Emacs helper's JSON-RPC in `src/emacs/protocol.ts`, with its handler in `src/server/http/socket.ts`, `AgentpaneApi.fork` in `src/client/api.ts`, and the helper's handler.
   The server's fork stays as the half of `forkAndPrompt` it already is.
   The `unwatch` bit on `sessions/abort` and `sessions/fork` goes with it, and so do `agentpane--forking`, `agentpane--refuse-forking` and `agentpane--fork-at`.
   A fork in flight then lives only in the helper's `forksOut` (D32 point 4), keyed by the session, which covers OW-tukuvo's sibling buffer.
4. **agentpane-mode marks the user messages a fork point names, from fork points the Emacs helper holds.**
   The helper fetches an attached view's fork points through the server's `sessions/forkPoints` at its snapshot and at each edge of its streaming, keyed by handle with at most one fetch out per handle, as the browser's `refreshForkPoints` does, and sends them to the view as a notification; a failure is quiet and leaves the last set standing.
   agentpane-mode only draws: a user message a point names carries a ✎ mark, drawn as plain text where the browser draws its control, and one no point names carries none.
   Until a view's first set has arrived every user message is offered, as the browser offers them while its set is unknown, and the server refuses a send at a message no point names (`not_a_fork_point`).
   A preview shows no marks and no set is fetched for it, since `sessions/forkPoints` serves only an attached session (OW-sirofi), as the browser offers no ✎ on one.
   `f`, `e` and `C-c C-e` read the held set rather than fetching at the press, as the browser's `startEdit` does, and on a message not in it they say it cannot be forked at.
   The edit's hint about stopping a running turn reads `forkStopsTurn` from the same set.
   The helper holds it, not agentpane-mode, by D32's direction that state logic lives in TypeScript; the coordinating session settled that on 2026-11-21, after a cold read of the issues.
5. **Both clients.**
   The capability is the browser's already, so this brings agentpane-mode to parity; the browser changes only by losing the plain fork it never used.

**What it amends.**
- **D15:** the client's abort before a Pi fork at `f` belonged to the plain fork, and goes with it; an edit's send sends none (D30), and `C-c C-e`'s stop at the press, the browser's "Stop and edit", stays.
- **D20:** agentpane-mode marks a message no fork point names as not editable before the press, as the browser does.
- **D30:** the plain `sessions/fork` it kept beside `forkAndPrompt` goes.
- **D25 and D31:** the plain fork's flag in the teardown, and the plain fork kept as a command until ark3/agentpane#17, go.
- **D32 point 6:** the temporary `unwatch` goes.

**Issues.**
1. ark3/agentpane#75: `f` starts the edit, and the plain fork goes from both wires (points 1 to 3).
2. ark3/agentpane#76: agentpane-mode marks the messages it can fork at (point 4).
