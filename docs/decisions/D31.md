# D31. One WebSocket carries commands, replies and events

The owner took this on 2026-11-19 (ark3/agentpane#42).
**Decided and built**: the server, both clients and the probes, so the prose describes the code as it stands.
Amended by D33 on 2026-11-21, and built by ark3/agentpane#75: the plain `sessions/fork` goes from the socket's commands.
Since ark3/agentpane#52 the server answers the socket at `SOCKET_PATH`, through `openConnection` in `src/server/http/socket.ts`, which `createApp` hands out as `connect`, with the frames in `src/shared/protocol.ts` (`Commands`, `ServerFrame`).
The first frame is a `hello` command carrying the token, whose reply follows the opening snapshots; a first frame that is anything else, or a wrong token, closes the socket 4401, and a frame that is not a JSON object with a string `id` closes it 4400 (`SOCKET_CLOSE`).
A refusal carries `fork` and `attached` beside `code` and `detail`, as D30's did on HTTP.
The limits chosen under point 8 are a `maxPayloadLength` of 32 MB (`MAX_SOCKET_FRAME_BYTES`), under which a prompt's images echoed in its upsert stay below the 40 MB measured to pass outbound, and, since ark3/agentpane#62, a `backpressureLimit` of 1 GB with `closeOnBackpressureLimit`, so a socket whose client has stopped reading is closed rather than left to drop a reply, and no amount of live transcript keeps a client from completing its `hello` (`docs/MANUAL_TESTING.md`, "The socket through agentpane's own binding" and "Live transcripts past 64 MB at a hello").
No frame the server sends is bounded yet: a snapshot carries its whole transcript, so one session past a client's own frame cap still cannot be shown there, and bounding it is deferred to ark3/agentpane#68 as of 2026-11-20 (point 8).
Since ark3/agentpane#53 both clients talk to it through `createAgentpaneApi` in `src/client/api.ts`, whose one `onmessage` handler applies each event and settles each reply.
`AgentpaneApi` kept its methods, and each command on a live session takes the handle in place of the ref (point 9); agentpane-mode sends the handle it holds on each, and reads a refusal by its `error` code where it read the HTTP status.
A request that was never written -- made with no socket up, held for an open that failed, or over `MAX_SOCKET_FRAME_BYTES` -- is refused with a code of the client's own, `unreachable` or `frame_too_large`, since it ran nothing; one written and unanswered at a close is the connection lost of point 6, or `unauthorized` at a 4401, since then too the server ran nothing.
The browser reopens on a fixed 5s delay, and a pasted token reopens at once; the Emacs helper opens its socket at the first request it reads, not at its start, so that with no server a failed open answers that request rather than ending the helper before it is read (OW-pezelo).
A second attach on a handle the helper already feeds is preceded by the server's snapshot going untagged to that handle's buffer, where the helper's hold of the reply had sometimes kept it back.
Since ark3/agentpane#54 the probes that drive agentpane's API are Bun, on the socket through `resources/probes/agentpane_live_support.ts`, and `AGENTS.md` carries the rule that new probes are written in Bun.
Since ark3/agentpane#56 the browser joins no reply to the stream and writes no session state from a reply: `handleOf` reads views alone, an attach's, a create's or a fork-and-prompt's reply only moves the selection (`selectAttached`), and compaction's phase is the server's.
Its `busy`, `sending`, `editingExternally` and model and effort flags are read at each publish from the controller's requests still out (`Outstanding` in `src/client/controller.ts`), with a `compacting` beside them that holds Compact and Send between the click and the server's first status; `busy` names the latest of them a gesture made.
The listing at each open is asked once: the first open's is `start()`'s, written behind the `hello`.
Since ark3/agentpane#55 HTTP answers the static bundle and the upgrade and nothing else: every other path under `/api` is a 404, behind the `Host` check, rather than the bundle's fallback, so a client still asking for a route that is gone is told so (`createApp` in `src/server/http/app.ts`).
The event stream went with the routes, and with it the broadcaster's SSE framing, `retry` directive and heartbeat, and `Bun.serve`'s `idleTimeout: 60`, so the socket's idle life rests on the runtime's pings alone (point 8); the failure mapper gives a code and no HTTP status (`classifyFailure` in `src/server/http/failure.ts`).
The plain fork stayed a command, `sessions/fork`, until ark3/agentpane#75 took it off both wires (D30, "What goes"; D33).

**Why D2 is revisited.**
D2 named its own condition: a client that needs constantly correlated replies.
D28 lists where that came true, each a place that joins a reply to the stream locally, and the class exists twice, once between the browser and the server and again between agentpane-mode and its helper.
The owner's measure for the fix was the fewest states and orderings the code has to be right about, across the whole system.

**The decision.**

1. **One path.**
   Each client holds one socket.
   Commands go in on it, and replies and events come out on it in the order the server wrote them.
   Queries go on it too, so a listing's reply is ordered against the events around it.
   HTTP serves the bundle and the upgrade and nothing else, which gives up D2's curl.
2. **The wire.**
   In: `{ id, cmd, ... }`, the id minted by the client.
   Out: `{ type: "event", event }`, and `{ type: "reply", id, ok: true, result }` or `{ type: "reply", id, ok: false, code, detail }`.
   An HTTP status becomes a `code`, from one mapper.
3. **What a reply means.**
   The command was admitted or refused, and everything it caused while it ran was written before the reply.
   What a turn emits after its prompt is admitted comes after it.
   A reply's handler writes no session state (D28), and may take the state it reads to be at least as new as the reply.
4. **Handling in arrival order.**
   One function in each client applies events and settles replies, in the order they arrive.
   A single ordered channel does not give that by itself: jsonrpc.el 1.0.29 ran a reply after later notifications over one pipe (D24).
   As of `bun 1.4.4` and Chromium 157.0.8103.78, each handled one message per task, every continuation a message started running before the next message; `bun 1.4.0`, which the home server runs, ran the first two messages' handlers before either's continuations (`docs/MANUAL_TESTING.md`, "What a WebSocket does under Bun and in Chromium (D31)").
   The clients rest on rule 3 and not on that measurement, so the one function does a message's work before it returns, and defers none of it.
5. **The token is the socket's first frame.**
   A browser cannot set a header on a socket, as it cannot on an `EventSource`.
   The server sends nothing and runs nothing on a socket until a first frame has carried the token.
   The `Host` and `Origin` checks stay on the upgrade.
   D29's exemption for the event stream goes with the stream.
6. **The socket is up, or everything is detached.**
   A closed socket detaches every view the client held (D25 point 3) and settles every request still out as connection lost, its outcome unknown, with the draft kept.
   The browser reconnects on a fixed delay of its own, where a native `EventSource` retried forever looking healthy; the Emacs helper exits (D25 point 4).
   This is the rule ark3/agentpane#26 asks for.
   A turn-done watch on a turn seen streaming raises at the close, and every watch is then dropped, in both clients, since a close is taken to mean the server exited (D25 point 3).
   agentpane-mode did this at its helper's death, a deliberate shutdown aside (D25 point 4), and since ark3/agentpane#72 its helper does it at its socket's close, raising nothing when its input ends (D32 point 6); the browser kept its watch across a drop, where after a restart it waited forever.
7. **Each client draws the server's state.**
   Compaction's `"requesting"` is no longer written at the click.
   `busy`, `sending` and the pending model and effort sets in `src/client/controller.ts` become reads of the requests still out.
8. **The runtime's limits are set, not inherited.**
   As of `bun 1.4.0` and `bun 1.4.4` the default pings kept an idle socket open and `Bun.serve`'s `idleTimeout` did not reach an upgraded one, so the socket needs no heartbeat.
   On both, an inbound frame past 16 MB closed the whole socket, so `maxPayloadLength` is chosen for a prompt with images, and a client refuses a prompt over it before sending.
   Two ceilings bound what goes out, and a `hello` meets both, since it writes every live session's snapshot and then its reply in one run.
   The first is what one socket buffers, `backpressureLimit`: as of `bun 1.4.0` on the home server on 2026-11-20, a run buffered past it closed the socket with the reply unsent, and a client refused its `hello` cannot close the session that caused it.
   So the limit is set far above any real total, at 1 GB, and bounds only what the server holds for a client that has stopped reading.
   The second is one frame, which the receiving client caps: as of `bun 1.4.0` on the home server on 2026-11-20, Bun's client, the Emacs helper's, took a 100 MB frame and closed 1009 on a 130 MB one; Chromium's cap is not measured.
   Keeping every frame the server sends under that cap is deferred to ark3/agentpane#68 as of 2026-11-20.
9. **A live session is addressed by its handle, and a conversation by its ref.**
   Every command that acts on a live session names the handle the client holds for it, and is refused where that handle has ended.
   So a command that crosses a close and a re-attach cannot land on the new session, and nothing sent for a Pi fork's parent can reach the fork.
   Attach, preview, create and the listing name a ref, since they have no handle to name.
   D30 gives the prompt its handle first, where it changes what the server does; the other commands take theirs when these frames are defined, so no HTTP route is reshaped only to be deleted.
   A close can arrive while an attach is still starting, before any handle exists, so a close may still name a ref; whether it keeps that is ark3/agentpane#27's to settle.

**The Emacs helper's wire.**
The helper becomes a socket client, and JSON-RPC over stdio between it and Emacs stays (D22).
The helper's hold of an attach's reply until its snapshot, and its wait for the stream's open before a first request, go: the reply follows the snapshot, and there is no second connection to register.
"The reply binds nothing and the tagged snapshot binds" stays, since it is what covers jsonrpc.el.
Attach tokens and `agentpane--absorb` were ark3/agentpane#39's, and D32 retires both on 2026-11-20, built by ark3/agentpane#70: every per-session request and notification on the helper's wire names the buffer's view, and agentpane-mode merges no buffers.

**What it retires.**
`handleOf`'s read of the summary an attach's reply left, and compaction's two accepted races (D28).
`pendingFollow`'s re-check of the transcript on every update was listed here too, and stays: the user's message reaches the transcript after the prompt's reply on Pi and on a steer, which is the backend's order and not the transport's (D28).
The window between a listing's live read and a client's registration (D21).
`src/emacs/sse.ts` and the browser's `EventSource`.

**How it is tested.**
`createApp` gains a connection entry point that takes a `send` function and returns `receive` and `close`, with no runtime types, and a test passes a `send` that pushes into an array.
`AgentpaneApi` in `src/client/api.ts` keeps its shape over the socket, so the controller, the helper and `e2e/`'s synthetic one are not rewritten for the transport.

**Probes.**
New probes are written in Bun, and the probes that drive agentpane's API are ported to it with their support module, in the change that moves them to the socket; `AGENTS.md` gains the rule there (owner, 2026-11-13).

**Declined.**
Half-duplex long-poll: no events arrive while a command is in flight, so a slow command needs an outcome reported later anyway.
SSE with emptied replies: a 404 or a validation error has no handle's sequence to sit in, so two paths remain for failures, and the outcome needs either a requester the server can address or a pending entry in the transcript.
A cursor on the reply: a central guard over two paths, not one path.

**Order of the build.**
D30's operations first, over today's HTTP.
Then the socket beside HTTP, the clients moved behind `AgentpaneApi`, the probes ported, and last the HTTP command routes, the event stream and the joins deleted.

**What it amends.**
D2: the transport, and its accepted cost that ordering is not guaranteed across two channels.
D28: the rule stands, and nothing is left under "What does not follow it yet".
D29: the token arrives in the socket's first frame, and no route is exempt.
D25 point 1: every command on a live session but the close carries its handle, where that point judged one not worth a wire field; points 3 and 4: a closed socket is the drop they describe.
D21: the listing at each open is asked on the socket.
D11: the wire contract in `src/shared/protocol.ts` changes with it, and this is the raise that file asks for.
