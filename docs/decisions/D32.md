# D32. agentpane-mode's buffers are views the Emacs helper routes by, and the helper holds what a view has in flight

The owner took this on 2026-11-20 (ark3/agentpane#39), on the census ark3/agentpane#65 wrote into that issue.
**Decided, and built in full:** points 1 to 3 by ark3/agentpane#70, points 4 and 5 by ark3/agentpane#71, point 6 by ark3/agentpane#72, point 7 by ark3/agentpane#73 and point 8 by ark3/agentpane#74.

**What the census showed.**
Taken at d55d3add, `emacs/agentpane.el` held 41 buffer-local variables and 11 global ones that are state.
Most of what was not drawing, the draft or an edit fell into three classes: copies of what the helper or the server already knows, defences against an order of arrival, and state that exists only for what jsonrpc.el forces.
Three mechanisms carried most of it.
The first is attach tokens, minted per attach and released by every detach and close, because a snapshot that answers an attach must find the buffer that asked, which may hold another ref, or none, and no handle yet.
The second is `agentpane--absorb`, 146 lines, which merges a buffer into another once their attaches land on one handle, carrying drafts, windows, tokens, in-flight flags and the turn-done mark.
The third is a per-buffer in-flight flag for each kind of request, cleared by each request's own failure path. Because jsonrpc.el 1.0.29 answers only some requests at a helper's death, `agentpane--requests-out` existed to answer the rest.
The browser holds the same facts once, as reads of its own requests still out (`Outstanding` in `src/client/controller.ts`, ark3/agentpane#56), and holds no merge, since it has one selection.
#39's direction, from the owner on 2026-11-01, is that state logic belongs in TypeScript shared by the web UI and the Emacs helper, not in elisp.

**The decision.**

1. **A buffer is a view.**
   agentpane-mode mints a view id when it makes a transcript buffer, and the id never changes.
   Emacs mints it, not the helper, so that it outlives a helper's death.
   Every per-session request names its view, and the helper holds each view's binding: the ref it shows, and the handle it holds, if any.
   The helper sends every per-session notification under the view.
   agentpane-mode sends no attach token and no handle; the helper fills in the handle from the view's binding.
   A view's binding changes at a request from that view, and also when the helper handles the server's `ended` under its handle or a `seq` gap, which reach it on their own.
   Stdin is ordered, so a request reaches the helper under the binding the buffer had when it sent it, or under none once an `ended` or a gap has taken it; a request on a live session from a view bound to none is refused `not_attached` as before.
   A prompt is the exception that could go astray, since one from an unbound view goes by ref (point 4) and by ref it would resume a session another client closed, which D30 and D31 point 9 forbid; so a prompt the buffer sent while it held a handle carries `live`, and the helper refuses it `not_attached` from an unbound view rather than sending it by ref.
   That keeps D31 point 9.
   ark3/agentpane#70 corrected this point, which first said a view's binding changes only at a request from that view.
   A killed buffer detaches its view, and a notification for a view no buffer holds is dropped.
   The reply still binds nothing (D25, OW-rebawa): the snapshot under the view does.
   This answers #39's question of whether a buffer's binding could be fixed from the moment it exists: it is the view id, and what the view is bound to is the helper's to track.
2. **One view per handle, and no merge.**
   An attach, or a prompt naming no handle, from view B that lands on a handle view A holds binds nothing for B, and its reply names A.
   agentpane-mode shows A in B's window and leaves B a preview, with its draft still in it.
   The cases that reach this are a buffer previewing a ref an attached session was renamed onto, such as a stale listing row or a Claude Code `pending-` id, and an alias.
   The owner accepted the cost on 2026-11-20: a draft stays in the second buffer rather than being carried over.
3. **A buffer that a request will make is made before the request.**
   `agentpane-new-session` and an edit's send make their buffer first, not shown, under a new view id, and a refusal that names no session kills it.
   So a view with no buffer always means a buffer that has been killed, and the tokens that named a buffer not yet made go.
   A create the user quit waiting on fills its buffer when the snapshot comes, as before (D30).
4. **The helper holds each view's requests still out, and applies the browser's rules.**
   A second send from a view is refused `busy`, a prompt and a fork and prompt counting together as the browser's one `"submitting"` does.
   While a `sessions/compact` from a view is out, a send or a second compact from it is refused `busy` too, as the browser's `compacting` holds Send and Compact from the click to the reply.
   A second attach from a view joins the first `sessions/attach`, `sessions/create` or by-ref prompt still out from it, sending the server nothing and answering as that one does.
   A prompt from an unbound view whose attach is out waits for that attach, then names the handle it bound; where it bound nothing, or landed on another view's handle, the prompt is refused with the attach's error or `not_attached`, naming that view, and never goes by ref.
   A prompt from an unbound view with no attach out goes by ref (D30).
   So agentpane-mode sends one `sessions/prompt` carrying its view and text, and the helper chooses among those cases.
   While a fork and prompt is out, the helper refuses an attach, and a prompt by ref, of the session it forks, from any view, with the code `forking`.
   The refusals agentpane-mode made and the browser does not go, for parity (owner, 2026-11-20): a close while an attach is out, a second close, and every refusal while a close is out, of an attach, a refetch, a rename, a send, the fork points' fetch and an edit's send.
   The browser's refusals are the reference, in `src/client/App.svelte` (`detachable`, `renamable`, `send()` and the Send and Compact buttons' `disabled`) as well as in `src/client/controller.ts`.
   So agentpane-mode keeps refusing a close while it sends or compacts and a rename while it sends, and keeps its own record of its send in flight, refusing a second send before the helper's `busy` could reach it.
   Compaction's `"requesting"` mark goes, and nothing in agentpane-mode stands in for it: the helper's `busy` holds Send and Compact from the click to the compact's reply, and agentpane-mode refuses them while the server's status reports a compaction (D31 point 7), which that status does from before the reply (D31 point 3) until the compaction ends.
   Together the two cover the whole compaction, as the browser's `compacting` and `compaction !== null` do.
   ark3/agentpane#71 corrected this point, which first counted a rename while sending among the refusals agentpane-mode alone made, having read the browser's in its controller alone, and held Send only from the click to the server's first status.
5. **A close still out is refused by neither client.**
   An attach that arrives while a close is disposing waits the disposal out and then starts a fresh agent (`#disposing` in `SessionManager.attach`).
   A pane reads detached at the `ended`, ahead of the close's reply, so a press then is the user asking for the session back (owner, 2026-11-20).
6. **Turn ends come from the helper.**
   It hosts the browser's watch, `watchSubmit`, `watchAbandon`, `watchSessions` and `watchClose` from `src/client/favicon.ts`, and its row marks, `foldSessionTurns` from `src/client/session-turns.ts`, over the views its reducer already holds.
   It sends `session/turnEnded` for every live session whose turn ends, saying whether this Emacs's prompt was watching it.
   A submit arms the watch only where none stands, and its disarm takes down only what it armed, as in the browser; agentpane-mode's per-prompt count of claims (OW-kakasu) goes, by the owner's call on 2026-11-20.
   At a socket close the helper raises each watch that has seen streaming and then exits (D31 point 6).
   When its input ends, as at `agentpane-shutdown`, it raises nothing (D25 point 4, OW-nuzoto), so it is the helper, not a mark on the process, that tells a shutdown from a death.
   A gap drops the watch on its handle and raises nothing (D25 point 5).
   agentpane-mode keeps what windows show and what has been seen.
   Of `foldSessionTurns` the helper keeps only the level half, the last `isStreaming` it saw under each live session's handle, sending `session/turnEnded` at each fall from true to false: that function's selection and the marks it keeps are agentpane-mode's, which marks a session's row unless a window shows it, with or without a picker open, as the browser's sidebar marks it (D26).
   At the server's `ended` a watch that has seen streaming raises, as agentpane-mode raised before this decision; the browser leaves such a watch waiting and raises nothing, a difference between the clients older than this decision and left for its own issue.
   A helper that crashes, or is killed, raises nothing: only a socket close raises (D25 point 4).
   ark3/agentpane#72 corrected this point, which first had the helper host `foldSessionTurns` whole.
7. **The helper answers every request still out when its socket closes, and only then exits.**
   The answer is an error carrying a code of the helper's own, which reads as an outcome unknown, never as a server refusal.
   As of jsonrpc.el 1.0.29 on Emacs 31.1, `jsonrpc--process-sentinel` calls each pending error handler with `-1` but leaves the continuations in place, and the dead helper's last messages are handled after it, from timers (`jsonrpc--process-filter`). That is source read on 2026-11-20, and measured on 2026-09-28 as OW-bukupu.
   So those replies reach their requests, and agentpane-mode keeps ignoring `-1`.
   agentpane-mode keeps no record of requests out.
   A helper that crashes leaves some requests unanswered. Once points 4 and 6 are built, nothing in Emacs waits on an answer except the release of text queued behind a send, and the teardown resets that.
   ark3/agentpane#73 built it with the code `-32001` and no `data`, so nothing that reads a refusal's `error` matches it.
   At a close the helper writes these answers after its `session/turnEnded` raises, and resolves only once every one is written: under Bun 1.4.0, run on 2026-11-21 against a stand-in socket, it otherwise resolved ahead of them at an input's end.
   It answers at an input's end as at a socket close, since either way the requests are lost with the socket.
   The teardown resets, in every transcript buffer, the send in flight with the text held behind it, the plain fork's flag and an edit's fork buffer, and a request made through a helper that has exited, before its teardown, sends nothing and runs its failure path at once.
8. **`session/status` and `session/snapshot` carry `defaultEffort`** on the Emacs wire, from the helper's model list, which it asks for once per backend.

**What stays agentpane-mode's.**
- Drawing, the draft and the edit, all of which #65's census lists as Emacs's own.
- Which window shows which buffer, and the "seen" half of the turn marks.
- Whether a buffer is live, read from `session/snapshot` and `session/detached` and from the helper's death, as D25 and D26 have it.
- `agentpane--latest-request`, so that a preview's reply cannot draw over a newer view.
- The status as drawn, and `agentpane--read-idle` at a let-go.
- The four synchronous requests.
  While one is out, jsonrpc.el still runs a later async reply after notifications that followed it (D24). That no longer matters, since no reply binds a buffer or clears state.
- The teardown's deferral behind the helper's last messages (`agentpane--helper-exited`), since point 6's raises at a close are among those messages.

**The census's doubts.**
The census flagged five of its calls as doubtful. The decision settles each:
- A buffer moving to a newer handle by its ref was read from the code, not run. Whether it can happen no longer matters, since the helper never routes by ref.
- The Pi parent's second detach at the fork's reply is the plain fork's, which ark3/agentpane#17 retires. For a fork and prompt, point 4's refusal of the parent's attach while the request is out covers the case.
- The census classed attach-token correlation as a jsonrpc.el artefact, but buffers made by a create or a fork need it too. Point 3 answers that half.
- The "one attach at a time" removal measured having no queue at all. The join in point 4 keeps the behaviour the queue's tests pin.

**What it amends.**
- **D24:** a snapshot that answers an attach is sent under the attaching buffer's view, where it carried the attach's `token`. agentpane-mode merges no buffers, and OW-danifa's merge goes with `agentpane--absorb`.
- **D25:** OW-wukako's tokens and OW-nowihu's release of every token a buffer sent give way to the view. OW-mopuyi's teardown answering gives way to point 7. Point 4's raising of the turn-done watch at a helper's death becomes the helper's own, at its socket's close (point 6).
- **D26 point 7:** a buffer goes live again by a send or an attach from its view.
- **D30:** agentpane-mode's refusal of the parent's attach while a fork and prompt is out is the helper's (point 4), and that request, a create, and a prompt naming no handle carry the view where they carried a token.
- **D31:** "Attach tokens and `agentpane--absorb` are ark3/agentpane#39's" is settled here.

**What it deletes.**
#39 sets this as the target for its issues, measured against ark3/agentpane#67's baseline of 5,390 lines, 41 buffer-local variables, 11 global variables that are state, and 184 functions.
The forms deleted whole come to about 800 lines of `emacs/agentpane.el` at d62f38db, docstrings included.
`agentpane--request` (202 lines), `agentpane--send-prompt` (167), `agentpane-close-session` (103) and `agentpane--detach` (95) shrink by perhaps another 400 lines, which is an estimate and was not measured.
The buffer-local variables go from 41 to about 31, and the global ones that are state from 11 to about 5.
The helper grows, and each issue says which elisp mechanism its addition replaces.
