# D16. A prompt submitted mid-turn steers that turn, and a backend that cannot steer rejects

`submit()` during a running turn means *steer*: the text joins the turn already in flight, delivered at the backend's next safe point.
An adapter whose backend cannot do that rejects the submission rather than doing something else with it.
The owner took this on 2026-09-09 (OW-rifezo).
Amended by the owner on 2026-11-22 in ark3/agentpane#12, and not yet built, on the runs in `docs/MANUAL_TESTING.md`, "Pi's replies to a compaction and an extension command, on `pi 1.5.2`":
- **A Pi Stop's wait on the prompts before it is bounded** (ark3/agentpane#93).
  `PiAdapter.abort` sends its `clear_queue` once every prompt already written has been answered (OW-jifibo, below), and as of `pi 1.5.2` Pi answers a prompt naming an extension command only once its handler returns, so a handler awaiting `ctx.waitForIdle()` held the Stop until the turn ended by itself.
  The wait now ends 5s after the Stop, a first cut since no steer's preflight has been timed, and the `clear_queue` and `abort` go out then; in the same runs Pi took an `abort` behind such an unanswered command at once.
  A steer whose preflight outlasts the deadline meets what a bare abort did to one (OW-yewiku, below), and the `abort` itself stays unbounded, as `PiAdapter.abort` chooses.
  Asking Pi's `get_commands` which prompts are extension commands, and waiting only on the rest, was passed over for now, and so was dropping the wait.
- **Pi refuses a compaction while a turn runs, as Claude Code and Codex already do** (ark3/agentpane#94).
  As of `pi 1.5.2` a `compact` sent mid-turn aborts the turn and then compacts, so Compact during a Pi turn was a Stop.
  `PiAdapter.compact` refuses it, and both clients disable Compact while a turn runs, on every backend.
- **Each client waits out a Stop.**
  The browser's requests carry no timeout.
  agentpane-mode's `sessions/abort` took jsonrpc's default of 10s and dropped a later answer with its `:queued` texts, and it gets a timeout well past the deadline (ark3/agentpane#95).
  A prompt held behind a Stop now waits at most the deadline and the abort, inside agentpane-mode's 90s `agentpane--spawn-timeout`; the browser's half of that case, a request Bun's `idleTimeout` closed, predates the socket, which that timeout does not reach (D31 point 8).

Before this, the same user action did three different things and the composer drew one Send button over all of them: Codex threw `TURN_ACTIVE_ERROR`, Pi sent `streamingBehavior: "steer"`, and Claude wrote another user line to stdin.
Claude Code 2.1.267 settled that last behavior live on the home server (OW-jihete): a user line written after the first text delta was not acknowledged until after the first `result`, then ran as a separate second turn, while a `steer` control request returned `Unsupported control request subtype: steer` immediately.
The Claude adapter now rejects `submit()` while a turn is active, and applies the same single-flight gate to `/compact`, so no adapter path knowingly enters the CLI's queue.
The contract said only "resolves once the backend admits the turn", which all three honoured.

Steer is the pick because it is what a person typing mid-turn is asking for, and a follow-up delivers the text somewhere the user did not aim it.
Pi's own default for a message typed mid-turn is steer (as of `pi 1.2.0`, its interactive mode calls `session.prompt(text, { streamingBehavior: "steer" })` while `session.isStreaming`, in `dist/modes/interactive/interactive-mode.js`), which is corroboration and not the reason.
The alternative, standardising on follow-up, was the reachable-everywhere option and was declined: reaching it everywhere would have meant holding prompts server-side for Codex to simulate a primitive it does not have, in order to give every backend the weaker semantic.

Rejection is a real answer here, not a failure mode.
The server already refuses a prompt whose adapter throws, a 500 on the prompt route until D31 and a refused reply since, and `controller.ts`'s `submit` clears the draft only on success, so a rejected mid-turn prompt leaves the user's text where they typed it.
What an adapter must not do is silently downgrade to a follow-up, which is indistinguishable from success at the wire and puts the prompt after the turn without saying so.

Pi steers, Claude rejects because its backend cannot steer, and Codex steers.
Pi's half of that was the last one resting on a reading rather than a run, and it was measured on the home server on 2026-09-14 against `pi 0.85.1` (OW-yuyofu), six runs through the built server on the production spawn chain.
A prompt posted while a turn was streaming came back 202, and **the one thing that tells a steer from a follow-up is that Pi named the queue it went into**: `queue_update` came back with the text in `steering` and `followUp` empty, in every run.
That single fact carries the conclusion.
The other fact the runs establish is necessary for this decision but does not discriminate: the marker was answered without the session ever returning to idle — `agent_settled`, which `src/server/adapters/pi/reducer.ts` maps to `isStreaming: false` and which is therefore the boundary this decision is written about, fell nowhere between the request and its answer in any run.
That rules out a follow-up delivered *after* the turn, which is the failure mode this decision names; it does not rule out a `followUp` queue drained inside the same span, because the reducer's own docblock records that an `agent_end` can be followed by queued continuations.
So the queue name is the evidence and the boundary is the corroboration, not two independent readings agreeing.
Two finer signals deliberately decide nothing: Pi's `turn_start`/`turn_end` bound one LLM round and carry no id at all, so OW-tifuha's "same turn id" reading has no Pi equivalent and could not have one — `resources/fixtures/pi/tool-read.jsonl`, captured long before any of this, already holds two of those pairs inside one `agent_start`…`agent_settled` span — and `agent_end`, the inner agent loop, came out both ways across the runs depending on how much the model had left to say.
Two things that measurement does not reach: no run cut an in-flight assistant message short, and `streamingBehavior: "followUp"` was never sent, because the adapter never sends it — what Pi would do with one is inference here and not measurement.
Pi's documented "deliver after the current tool batch" was measured separately, on the home server on 2026-09-30 against `pi 0.87.1` (OW-nufitu), four runs: with three `bash` calls from one assistant message executing in parallel and one already ended, Pi put the prompt in `steering` while the other two were still running, let both finish, emitted all three `toolResult` messages, and delivered the steered user message only after that round's `turn_end`, as the first message of the next round — never between calls or between results, and still inside the one `agent_start`…`agent_settled` span.
A sequential batch, which `pi` 0.87.1 runs only when a tool declares `executionMode: "sequential"` or `toolExecution` is set to `"sequential"`, was not exercised; neither held in those runs, and no built-in tool in 0.87.1 declares one.
`docs/MANUAL_TESTING.md`, "A prompt posted mid-turn is steered into Pi's running turn" and "Pi's steer waits for the whole tool batch", carry the runs.
`turn/steer` was run live on the home server on 2026-09-12 against `codex-cli 0.154.0` (OW-tifuha): fired 29 deltas into a streaming turn with `expectedTurnId` set to that turn, it returned a result naming the same turn id, and both the steered `userMessage` and the answering `agentMessage` arrived under that turn id, with exactly one `turn/completed` and no second turn.
The Codex adapter's `submit()` now sends `turn/steer` whenever it holds a `turnId`, which since ark3/agentpane#84 only `turn/started` sets (D34 point 5).
Between a `turn/start` and its `turn/started` there is no id to put in `expectedTurnId`, a precondition, so a prompt reaching the adapter then is refused; `submit()` answers only once that `turn/started` has come, so a prompt `SessionManager` queued behind it runs once the turn is live, and steers.
`compact()` keeps its rejection regardless, and `submit()` gained one of its own for the same reason: `compact` is one of the two `NonSteerableTurnKind`s and a compaction runs as its own turn, so a `turnId` naming a compaction is a turn app-server will refuse to steer.
OW-jihete's fixture and OW-tifuha's section in `docs/MANUAL_TESTING.md` preserve both observations.

The effect on the accidental double-submit OW-nasofa describes — a second Ctrl-Enter during the round trip, which `App.svelte`'s `send()` and `controller.ts`'s `submit()` both fail to guard — runs in both directions, per backend.
On Claude it is an improvement: a silently queued duplicate becomes a rejection with the draft intact.
On Codex it is a regression now that OW-tifuha has landed: the former clean rejection is a duplicate steered into the running turn.
On Pi nothing changes, because Pi already steers it.
So this decision does not remove the need for OW-nasofa's in-flight guard, and on one backend it is what will make that guard load-bearing.
That guard is now built: `controller.ts`'s `submit()` returns while `sending` is set (OW-nasofa).

Steering also cost Codex an invariant the fork path leaned on: a steered turn holds two user messages where `listForkPoints` answers one point per turn, so the ordinal `controller.ts` computed by counting user messages no longer indexed the fork-point list.
That desynchronization was OW-roveze, and it was silent — a later Edit forked at the wrong turn rather than failing.
D20 below retires the counting; the invariant is gone rather than restored, and the steered message is simply not a fork target.
The narrower window between `abort()` and `turn/completed`, where a steer hits a turn being torn down, is OW-pefawi.

A steer sent *before* Stop and not yet delivered when the abort goes out is a different case, and on Pi a bare `abort` answers it the way the user asked in neither of the two ways it can go.
Measured on the home server on 2026-10-15 against `pi 1.2.0` (OW-yewiku), Pi alone, a steer queued behind a running turn and then a bare `abort` as `PiAdapter` sent it before OW-wisifo: nothing ran on its own after the abort in any run, and where the text went depended on what the turn was doing.
Stopped mid-tool, the aborted run delivered it as a user message whose reply failed at once with `stopReason: "error"`, so it stays in the session's messages as a turn nobody answered.
Stopped mid-reply, it stayed queued and was delivered into the next prompt's run, after that prompt, and that run's one reply answered the steer, or went back to the interrupted reply, but never the new prompt.
Sending `clear_queue` before `abort` took it out in both cases, and nothing leaked.
`docs/MANUAL_TESTING.md`, "A bare abort leaves an undelivered Pi steer unanswered in the transcript or inside the next prompt's run", carries the 22 runs, `clear_queue`'s response, and where Pi's own `rpc-commands.md` ("`abort` continues queued messages when they remain in the session") does and does not match.

The owner decided on 2026-10-15 that Stop does what Pi's own interactive mode does with Esc, as of `pi 1.2.0` (`restoreQueuedMessagesToEditor` in `dist/modes/interactive/interactive-mode.js`).
agentpane sends `clear_queue` before `abort`, and the text of every steered prompt Pi had not delivered goes back to the composer of the client that pressed Stop, so nothing runs after Stop and the words the user sent are not lost.
What comes back is what Pi queued, which as of `pi 1.2.0` is text only, so a steered prompt's images do not come back, and is the text after Pi's own expansion of a skill or prompt template.
The text goes back as the abort request's answer, not as a broadcast, because the composer to refill is the one that pressed Stop.
OW-wisifo carries it onto the adapter, the HTTP API and the Emacs helper's JSON-RPC, and settles whether `compact()` and the abort ahead of a Pi fork do the same.
It settled them on 2026-10-15, each recorded where the call is made: `PiAdapter.compact` does not clear the queue, since nothing on either wire would carry the texts back; the abort ahead of a Pi fork clears it and drops what it took out, in both clients; and `PiAdapter.submit` refused a prompt while a stop was awaiting Pi's answer, which would otherwise steer into the queue just cleared.
OW-jifibo replaced that refusal the same day with an order `PiAdapter` keeps on Pi's stdin: a stop sends its `clear_queue` only once every prompt already written has been answered, since as of `pi 1.2.0` Pi answers a steer `queued` only once it is in the queue the clear empties (read at the installed package, not measured), and a prompt sent while a stop is in flight waits for it and then goes out, so Stop then Send starts a fresh turn.
`PiAdapter.abort` says what that costs when Pi never answers the abort, and what happens to the texts when the abort fails after the clear.
OW-fahoti and OW-seleri, both blocked by it, put the text back in each client's composer, including under "Stop and edit", where the composer already holds the message being edited.
Until both land, a build carrying OW-wisifo clears the queue and a client that ignores the answer shows nothing, so those three are one change landed in three cards and are run together.
