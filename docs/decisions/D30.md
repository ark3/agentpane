**The rule.**
If every step of a sequence must complete once the first has run, the sequence is one operation and the server runs it.
If the user can reasonably stop between two steps, it is a flow and stays in the client.

There are two clients, so a chain kept in the client is written twice, and each `await` in it is a window in which the user can click elsewhere or the client can go away.
`forkAndSubmit` in `src/client/controller.ts` is up to five requests deep, and agentpane-mode has its own copy (`agentpane--fork-points`, `agentpane--fork-at` and `agentpane--send-edit` in `emacs/agentpane.el`).
The server can also do what no client can: run the chain as one item on the session's queue (D24), and finish it whether or not a client is still watching, which is what D17 already promises.

**The operations.**

1. **Fork and prompt.**
   It takes the session, the transcript index of the user message to fork at, and the prompt's text and images.
   It acts on an attached session or refuses, as a fork does today (D25).
   As one item on the parent's queue it resolves the index against the adapter's fork points, refusing where no point names it (D20), and forks.
   Where the backend abandons a running turn at a fork whatever agentpane does, which is Pi (D15), the adapter's own `fork` stops that turn first, so neither the session manager nor a client tests for the backend.
   It then attaches the fork and prompts it, and answers once that prompt is admitted, with the fork's live summary and the prompt's disposition.
2. **Create attaches.**
   Both clients attach a session the moment they create it, so creating one starts its agent and answers with its live summary.
   A start that fails leaves nothing behind: the container goes with every name it took, and a retry is a new create.
3. **A prompt is addressed to a handle or to a ref.**
   One sent from a view that holds the session live names its handle, goes to the live session under that handle, and starts nothing: where the handle is gone it is refused `not_attached`, with the text kept.
   One sent from a view that knows the session is not running names only the ref, and the server attaches the session if it must and then prompts it.
   This replaces agentpane-mode's attach, then send, from a detached buffer (`agentpane--attached-then`).
   The browser draws no composer on a detached session, so it always names a handle.

**What stays in the client.**
Whether the selection moves to a fork, which D17 gives to the user's latest click.
Clearing the draft only while it still holds the text that was sent.
One send at a time.
Opening and cancelling an edit, "Stop and edit", and choosing a new session's model and then its effort: the user can stop between the steps of each.

**How a client recognises the fork it asked for.**
The operation's reply names the fork's handle, and no token is minted for it.
Over HTTP the reply could precede the fork's snapshot, as an attach's could, and the same join covered it (`applyAttached`); on D31's socket the reply follows that snapshot, and since ark3/agentpane#56 it only moves the selection.

**A fork that lands and is then not prompted.**
The failure goes to the requester, as the operation's refusal, and that refusal names the fork where one was created.
Both clients keep the text.
Where a fork is named they end the edit and move to the fork, so that sending again prompts that fork; left on the parent with the edit open, a second send forked again and orphaned the first (ark3/agentpane#17).
Where none is named, nothing was created and the edit stays open.
The server does not remove the fork, for D17's reasons.

**The label follows the server.**
The fork-points answer says whether a fork of that session will stop a running turn.
Both clients read "Stop and fork" and its equivalents from that, where the browser tests the backend in `src/client/App.svelte` (`stopsBeforeFork`) and agentpane-mode says nothing (ark3/agentpane#17).

**What goes.**
The fork route, once agentpane-mode's `f` starts an edit as the browser's pencil does (ark3/agentpane#17), since no client then forks without prompting.
Creating a session without attaching it.
The fork-points query stays: it is what marks a message editable (D20).
The probes that drive agentpane's API drive the operations.
"A fork is in flight" needs no flag in either client beyond its own outstanding request: the parent's queue owns it (ark3/agentpane#17).

**Both wires.**
Each operation goes on the HTTP API, the socket since D31, and on the Emacs helper's JSON-RPC (`src/emacs/protocol.ts`).

**Built first, over today's HTTP.**
D31 changes how a reply is ordered against the stream, not what these operations are, so they land ahead of it.
