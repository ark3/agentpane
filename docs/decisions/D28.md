# D28. The event stream owns session state, and a reply only ends its request

The owner took this on 2026-11-13, after asking whether the races between the API and the event stream had ever been addressed as one thing.
They had not: the rule below was reached four times, each after a defect, and stated at each site and nowhere once.
Amended by D31 on 2026-11-19: one WebSocket makes the rule structural, and retires each join "What does not follow it yet" listed.
Both clients use it since ark3/agentpane#53, which retired the helper's join, and ark3/agentpane#56 retired the browser's.

**The rule.**
While a client's stream is up, what it knows about a session comes from the stream.
A reply to a request tells the requester that the request ended and how, and a client writes no session state from it.
D2 was why: two unordered channels made a client that writes state from both get every interleaving right, where one that writes it from the stream alone has one ordered sequence to apply.
Since D31 there is one channel, and a reply follows everything its command caused while it ran, so a reply's handler may take the state it reads to be at least as new as the reply.

**Where it was reached.**

- An attach in agentpane-mode: the helper's notifications alone say a buffer is attached, and the reply only ends the request (D25, OW-rebawa).
- A turn's error: the `error-cleared` event drops it, and the prompt's reply does not (OW-lohubo, `submit` in `src/client/controller.ts`).
- A session's end: `ended` is the one owner of a handle having ended (D26 point 4).
- A row's `status`: the listing alone owns it (D25, OW-forinu).

**What a reply still carries.**
A refusal or a failure, which is the requester's alone; a value only the requester asked for, such as abort's queued prompts, the external editor's text, a listing, the models, the fork points or a preview; and the name of what a request created, an attach's handle or a fork's ref, which says where on the stream to look and is not itself the state.

**What does not follow it yet.**
Nothing: the rule is structural since D31.
Each command's reply comes on the socket after the events it caused (D31 point 3), and one function in each client handles both in the order they arrive (D31 point 4), so no site joins a reply to the stream.

What was listed here on 2026-11-13, found by following the comments that cite D2, went as follows.
`handleOf` in `src/client/session-state.ts` read the handle from the summary an attach's reply left, in the window before its snapshot; the window is gone, and so is writing a summary from a reply (ark3/agentpane#56).
Compaction wrote `"requesting"` at the click, with two races accepted (OW-natiha, OW-husivu); the client draws the server's phase alone, and its request still out holds Compact and Send (ark3/agentpane#56).
`sending` in `src/client/controller.ts` held a prompt's round trip apart from `busy`; both, and the pending model and effort sets, are read from the controller's requests still out (`Outstanding`, ark3/agentpane#56).
The Emacs helper held an attach's reply until the snapshot that answers it (D25), until ark3/agentpane#53.
D30 moved the chains of requests, each `await` of which was such a window, into the server.
`pendingFollow` in `src/client/App.svelte` still re-checks the transcript on every update, and is not a join: the backend writes the user's message into the transcript after the prompt is admitted on Pi and on a steer, so it comes after the reply there too, and the follow waits on the backend rather than on the transport (its docblock).
