# D28. The event stream owns session state, and a reply only ends its request

The owner took this on 2026-11-13, after asking whether the races between the API and the event stream had ever been addressed as one thing.
They had not: the rule below was reached four times, each after a defect, and stated at each site and nowhere once.
Amended by D31 on 2026-11-19, decided and not yet built: one WebSocket is to make the rule structural, and to retire each join under "What does not follow it yet".

**The rule.**
While a client's stream is up, what it knows about a session comes from the stream.
A reply to a request tells the requester that the request ended and how, and a client writes no session state from it.
D2 is why: the two channels are unordered, so a client that writes state from both has to get every interleaving right, and one that writes it from the stream alone has one ordered sequence to apply.

**Where it was reached.**

- An attach in agentpane-mode: the helper's notifications alone say a buffer is attached, and the reply only ends the request (D25, OW-rebawa).
- A turn's error: the `error-cleared` event drops it, and the prompt's reply does not (OW-lohubo, `submit` in `src/client/controller.ts`).
- A session's end: `ended` is the one owner of a handle having ended (D26 point 4).
- A row's `status`: the listing alone owns it (D25, OW-forinu).

**What a reply still carries.**
A refusal or a failure, which is the requester's alone; a value only the requester asked for, such as abort's queued prompts, the external editor's text, a listing, the models, the fork points or a preview; and the name of what a request created, an attach's handle or a fork's ref, which says where on the stream to look and is not itself the state.

**What does not follow it yet.**
The rule is a convention, and nothing on the wire enforces it: no event names the request that caused it.
So a site that needs both channels joins them locally, and these were found on 2026-11-13 by following the comments that cite D2, which is not a search of every request site.
`pendingFollow` in `src/client/App.svelte` re-checks the transcript on every update because the prompt's reply says nothing about what has arrived.
`sending` in `src/client/controller.ts` holds a prompt's round trip apart from `busy`.
Compaction writes `"requesting"` at the click, with two races accepted (OW-natiha, OW-husivu).
`handleOf` in `src/client/session-state.ts` reads the handle from the summary an attach's reply left, in the window before its snapshot.
The Emacs helper holds an attach's reply until the snapshot that answers it (D25).
D31 is the mechanism that retires them, and D30 moves the chains of requests, each `await` of which is such a window, into the server; D31's socket is built on the server (ark3/agentpane#52) and no client uses it yet, and D30's three operations are built, which both clients send (ark3/agentpane#47, ark3/agentpane#51, ark3/agentpane#48, ark3/agentpane#49).
