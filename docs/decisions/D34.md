# D34. An adapter takes state from its backend's events, and an attach that meets a running turn is refused rather than merged

The owner took this on 2026-11-21 (ark3/agentpane#44), choosing option A of the three that issue's cold read of 2026-11-20 set out: simple code for an uncommon case.
**Built**: the audit of points 3 and 4 landed with ark3/agentpane#77 in docs/BACKENDS.md, point 1 with ark3/agentpane#78 on 2026-11-21, point 2's assertion with ark3/agentpane#79, and point 5's moves of Pi's `isStreaming` after a fork onto `agent_settled` with ark3/agentpane#81, of Codex's name after a rename onto `thread/name/updated` with ark3/agentpane#82, of Claude Code's name onto `session_title_changed` with ark3/agentpane#85, of Pi's name after a rename onto `session_info_changed` with ark3/agentpane#80, and of Codex's running turn onto `turn/started`, the submission source replaced by a gate from the request to that event, with ark3/agentpane#84; ark3/agentpane#83 moved nothing, model and effort staying on Codex's replies, since as of `codex-cli 0.170.0` `thread/settings/updated` does not arrive on agentpane's connection.
Amended on 2026-11-22 by ark3/agentpane#86, a follow-up filed from ark3/agentpane#78: the Codex hydrate of a settled transcript is a replace, so the merge "What it amends" names under D24 no longer stands.
Its event waits are bounded since ark3/agentpane#91 on 2026-11-22, as a start is by D35 point 2: a Codex request that answers only once an event has come, `setName`'s `thread/name/updated` and the `turn/started` that `submit` and `compact` wait on, is refused when that event has not come 60s after the request (`eventTimeoutMs`), with one session error naming it, and the verbs queued behind it run.

**What stood.**
D28 says that between a client and the server the event stream owns session state and a reply only ends its request.
One boundary down, between an adapter and its backend, the adapters write some state from replies where an event carries the same fact, and rely on the order of the two in places no assertion guards (#44, "Reply/event pairs the leads missed").
The most intricate logic on that boundary is D24's hydrate merge: a Codex history page taken mid-stream leaves out the item still streaming, as of `codex-cli 0.156.0`, so a delta opens a headless slot, a listed copy later replaces it, and the running turn and its id are adopted from the listing (OW-vijuyi, OW-zudase, OW-dutute, OW-dirazu).
It serves one path: `start()` in `src/server/adapters/codex/adapter.ts` re-attaching a thread that a live app-server still holds and that is running a turn, through `startBorrowed` with `pageRequested`, after one side of a fork pair was closed and the other kept the app-server alive (OW-voyezi, `codex-cli 0.154.0`).
The browser withholds Detach while streaming and D12 spares streaming and compacting sessions, so that path takes a close sent as a turn was starting, or one sent straight to the socket, as read from the code on 2026-11-20.

**The decision.**

1. **An attach that meets a running turn is refused, not merged.**
   Where a Codex attach finds its thread running a turn, the adapter refuses it with a new refusal code, `turn_running`, on both wires, and starts nothing.
   It knows a turn is running from the one reply that says so, the resume's thread status, since on `codex-cli 0.156.0` `thread/resume` replayed no `turn/started` (D24).
   As built in ark3/agentpane#78, the adapter reads that status alone, straight after the resume and before any page, on a re-attach only, not a fork's first attach; it read `active` mid-turn on `codex-cli 0.170.0` too (`docs/MANUAL_TESTING.md`, ark3/agentpane#78), and the listing's `inProgress`, a later read of the same fact, is not consulted.
   Each client shows the refusal with a message saying the session's turn is still running elsewhere and to try again when it ends, as each shows `at_capacity`, and keeps the preview.
   The hydrate then merges only a transcript nothing is still writing to, so the merge's running-turn half goes: the headless slots, `sincePage`, the hydrate's `running-turn` effect, `pageRequested`, and the adapter's adoption of a listed running turn.
   D12's exemption is not blinded, since no session is adopted mid-turn: the refused attach leaves nothing live.
2. **Pi already hydrates only a settled session**, and this deletes nothing there.
   Since D30 (b653ca0e) `PiAdapter.fork` awaits `abort()` before it forks, and a resume spawns a fresh process.
   What Pi keeps relying on is an order: nothing arrives between `fork`'s answer and `get_messages` (`hydrateMessages`, OW-dutute, as of `pi 1.2.0`).
   That is a fact of D18's third group, and it gets D18's runtime assertion where the forbidden input would arrive.
3. **The audit's rule.**
   Where a backend sends both a reply and an event for one fact, the adapter takes the event, and the reply only ends the request.
   Where the backend gives no event, or the adapter must rely on the order of the two, that is a backend fact carrying its version (D18), and an order that licenses absent code gets a runtime assertion.
   D28's exemption covers a value only the requester asked for: `get_state`, `get_settings`, `thread/turns/list`, and a reply naming what its request created.
   A mutation reply that echoes state an event also carries is in scope.
   The coordinating session took that reading of #44's open definition on 2026-11-21, since the owner's choice settled the rest of the issue.
4. **The audit is recorded per backend**, in `docs/BACKENDS.md`, under a `### Replies and events` section in each of `## Pi`, `## Claude Code` and a new `## Codex`.
   Each fact an adapter writes from a reply is listed with the event that carries it, or "no event", and the version it was measured on, or the commit it was read from where no run measured it.
5. **Each move from a reply to an event is an issue of its own**, filed from the audit, since several need a measurement first and one, Codex's submission source, needs a replacement for the window it covers between `turn/start`'s reply and `turn/started` (`codex/adapter.ts`; the reply came first for all 15 `turn/start` replies in the 12 Codex fixtures that record the wire, `codex-cli 0.147.0` to `0.157.1`, `docs/BACKENDS.md`).
