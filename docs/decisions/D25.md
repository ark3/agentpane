**Why the routes attached first, and why that no longer holds.**
D12's OW-35 asked that a prompt to a session the server had reclaimed re-attach transparently, so that eviction would be invisible.
The owner, on 2026-09-28: that was written before any experience of attaching and detaching; the unattached preview is a mode worth having in its own right, and attaching is fast (1.138s for a re-attach on `pi 0.85.1`, OW-jamoyi).
The browser had already stopped prompting an unattached session: since OW-tewave and OW-jamoyi a preview replaces the composer with an Attach button.
Read on 2026-09-28 and confirmed by OW-sirofi the same day, neither client's deliberate paths needs a route to attach for it: the browser's `create` and `select` call `api.attach` first, and agentpane-mode's new session and its send from an unattached buffer sent `sessions/attach` first, a path D30 replaced with a prompt naming the ref.
The one exception it found is the browser's selected session closed by another client with the stream up: `replaceSessionSummaries` in `src/client/session-state.ts` drops the live view but leaves the selection and no preview, so the composer stays and its Send meets 409 `not_attached` where it used to respawn, which OW-zivamo filed; OW-forinu settles it by deriving the pane's mode ("What the run found", below).

**The decision.**

1. Only the attach route, the `GET` of `ROUTES.session`, spawns.
   Every other session route acts on an attached session or refuses, as `compact`, `abort` and `reply` already did.
   `close()` takes the container out of the table before its first await, so a request arriving after a close has begun is refused and nothing respawns, with no guard of its own.
   Requests do not carry the handle they were sent for: the one ordering that leaves, a stale request landing on a deliberate re-attach made after the close, respawns nothing, and was judged not worth a wire field.
2. D12's transparent re-attach is withdrawn, and OW-35 is declined.
   A reaper or cap, if one is ever built, evicts as a visible close, as Detach does: the session goes back to a preview and the user attaches it again when they want it.
   The rest of D12 stands, its unbuilt status and the reason for it included.
3. A client whose event stream drops holds nothing live: on the drop, every session it held is detached, at once.
   Agentpane is local-only, and on both machines it runs on a stream drops only when the server exits -- the owner stopping it, or Windows stopping WSL2 under the work laptop -- so a drop is taken to mean every agent is gone.
   The server announces no restart and neither client shows one; the owner, on 2026-09-28: every session detached is what they expect after a restart.
   D21's listing at a reconnect stays, and so do the server's opening snapshots, which re-introduce whatever is still live after a drop the server survived.
4. The Emacs helper exits when its event stream drops or its first open fails, and does not reconnect.
   agentpane-mode takes any helper's death to mean every buffer it served is detached, whatever the cause: a helper that crashed over a live server is rare, and costs an attach, since under D26 `g` previews a buffer that is not attached.
   Every death but a deliberate `agentpane-shutdown` is also taken to mean the server let go of each handle, so a turn-done watch on a turn seen streaming ends as an aborted turn's does and raises the indicator (OW-zedawo).
   A deliberate shutdown is not the server letting go: `SessionManager` in `src/server/http/session-manager.ts` disposes nothing when a client's stream closes, so the turn goes on unheard.
   The owner decided on 2026-09-30 that it raises nothing and drops the watch, `streamed` or not; a re-attach after a restart that finds the turn still running then raises nothing either, a case judged unlikely and cheap to lose (OW-nuzoto).
   A picker open at that moment goes stale until `g`, which the owner accepted.
5. A sequence gap detaches that one session, in either client, instead of attaching it to recover a snapshot.
   The handle stays live on the server and the turn may go on unheard, as at a deliberate shutdown.
   The owner decided on 2026-09-30 that a gap gets the same treatment in both clients: it raises nothing and drops the turn-done watch on that handle, `streamed` or not.
   The case given up is a turn the gap cut off, re-attached from the same buffer or tab while still running, and ended with nothing showing it; it needs a gap, which this decision already reads as something gone wrong, then a re-attach mid-turn, and costs one missed indicator, which was judged not worth the state that kept the watch for it (OW-bepudu for agentpane-mode, OW-jadoda for the browser).
   The owner decided on 2026-09-30 to give up the browser's fork window the same way: a gap on the fork's handle that lands before its attach replies does not drop the watch that reply then arms, so where a later snapshot re-forms the view under that handle, the turn's end there raises the badge this point withholds; it needs a gap inside a fork's short window, and costs one badge, which was judged not worth new state (OW-koledi).

The browser's pane stored its preview beside the selection and read "live" from the preview's absence, so each path that adds or drops a view kept the pairing by hand, and three of them slipped: a composer over no view (OW-zivamo, OW-wazija, OW-tefigi) and a preview over a live view (OW-tefigi).
The pane's mode is derived instead, by a fixed precedence: live when the tab holds a view of the selected session, and the composer only then; preview when it holds a preview and no view; otherwise detached and loading, which draws the Attach button over an empty pane, the owner preferring an honest empty pane to a stale transcript.
One place fetches the preview, once the stream is up, and the listing alone owns a row's `status`.
That is OW-forinu.
Built the same day: `paneMode` in `src/client/controller.ts` is the derivation, `publish` fetches the detached-loading pane's preview, and an attach reply keeps the listed row's `status`, a row no listing has named yet reading `detached`.
A stream drop now keeps a selection whose transcript is on disk, on the detached-loading pane, and until OW-lilami still cleared one with nothing on disk; since then it keeps that one too, with its row, and the preview's `gone` clears it once a server answers (D26 point 6).

agentpane-mode bound a buffer to a handle on two channels, the attach reply and the helper's snapshot, so a reply that landed after a gap or behind a synchronous request rebound a buffer the helper no longer fed (OW-tifiva, OW-kifuhi).
The helper's notifications alone say a buffer is attached: from a snapshot under its handle until a `session/detached` or the helper's death; the reply only ends the request.
That is OW-rebawa.
Built the same day: `agentpane--attach-by` in `emacs/agentpane.el` binds a buffer at the snapshot and merges into it one already holding the handle, the reply's callback runs an attach's waiters only if that snapshot has attached the buffer by then, and `agentpane--attached` is the one record, its sibling `agentpane--served-by` retired; the helper records an attachment only as it sends the snapshot that answers an attach, tags every such snapshot with the ref that attach asked for, one for each attach it answers, and writes the attach's reply only after it.
From OW-wukako (2026-09-30) until D32 the tag was a token agentpane-mode minted per attach, not the ref, as below; since ark3/agentpane#70 the snapshot goes under the view of the buffer that sent the attach, and the merge into it is gone.
The server writes an attach's snapshot to every connected stream before it answers, and a stream that connects later gets an opening snapshot of every live session, but the two channels are unordered (D2): on the fake adapters a direct client read the reply first in 23 of 40 attaches, whether or not the attach started its session, and the first build, which let the reply go, failed the waiters of 12 of 30 attaches that started their session.
So a reply whose attach no snapshot has answered waits for the one on its way, the view the helper holds going out at once where it has one, and goes out without a snapshot only when the helper expects none: a gap took the view after a snapshot under the handle came, a detach from the attach's view (until ark3/agentpane#70 a detach or close carrying the attach's token, and until OW-wukako any of the asked-for ref), an `ended` under the handle (until OW-likopo a listing without it, D26), or the helper's end.
The first can misjudge: a snapshot under the handle from elsewhere, ahead of the server handling this attach, then a gap, then the reply, and the attach's own snapshot arrives after the reply and answers nothing; it takes a lost or malformed frame, and ends with the buffer not attached, which point 5 accepts.
Since OW-wukako it reaches an attach of the session's own ref as well as an alias's, since no snapshot answers an attach before its reply any longer.
The synchronous requests were suspected and are not the cause: each of the four needs its answer before the minibuffer prompts, and once no reply binds and no cleanup rides jsonrpc.el's walk, what they disturb no longer matters.

The helper matched an attach to its answering snapshot, and a detach to the attaches it gave up, by the ref asked for: a detach from one buffer gave up another's attach of the same ref (OW-jofodu), and a snapshot under an older handle for that ref answered an attach whose reply then named the handle the server had since minted, so the buffer was bound to a dead handle (OW-savafi).
That is OW-wukako, decided and built on 2026-09-30.
agentpane-mode minted a token per attach and sent it on the attach and on every detach and close, which from OW-nowihu carried every token the buffer sent, not only its last; the helper kept each attach by it, tagged the answering snapshot with it in place of the ref, gave up only the attaches a detach's tokens named, and answered an attach only under the handle its reply names, from the view the reducer holds there or the snapshot still on its way.
D32 replaced the token with the buffer's view (ark3/agentpane#70), which the helper binds to the handle and every per-session notification carries; the last clause stands.
The server does not echo the token, or the view, on the snapshot an attach causes.
The reply already names the handle the attach landed on, so dropping the early answer by ref settled OW-savafi without a wire field; what the echo alone would add is telling the misjudgment above from a gap that took another snapshot, which takes a lost or malformed frame (D26 point 4).
Against that, it would put a field on the HTTP API that concurrent attaches, collapsing onto one startup and one snapshot in `SessionManager.attach`, would need as a list, and a new helper against an older running server would wait out every attach.
Judged as decision 1 judged a handle on other requests: not worth a wire field.

A buffer's in-flight flags were cleared only by each request's own failure path, which jsonrpc.el at a helper's death skips (OW-laluso) or runs before the teardown could see a turn had streamed (OW-zedawo).
Until ark3/agentpane#73 the teardown answered every request the dead helper had out and settled each served buffer, per point 4; per-request handlers owned every failure that was not a death.
That is OW-mopuyi.
Built the same day: `agentpane--request` in `emacs/agentpane.el` records each request it sends in `agentpane--requests-out` under its connection, and `agentpane--helper-gone` lets go of the buffers at once and answers every request still there as the death from a zero-delay timer of its own, running each one's failure path and never the path for a request that reached no backend, so the turn-done watch on a handle a served buffer holds is `agentpane--let-go`'s to settle.
The "Server died" jsonrpc.el's sentinel gives every pending request answers nothing: as of jsonrpc.el 1.0.29 it carries the code -1, which the helper never writes (`toRpcError` in `src/emacs/helper.ts`).
An error reply the helper wrote before it died is the request's answer, as one from a live helper is, and its message reaches the echo area; that is OW-hiliti, built 2026-09-29, and until then the error handler answered nothing once the helper read as dead, that reply included.
Only a refusal says the request reached no backend: an error whose `data` carries the server's HTTP status, as `toRpcError` builds it, so a prompt the server refused abandons its turn-done watch.
Any other error reply, the helper's own -32603 for a failed transport or -32601, leaves the outcome unknown, as a timeout does, and the watch stands for the teardown to settle: with the server killed and a prompt in flight, the socket's error reached the helper before the stream's drop, and read as a refusal it abandoned the watch of a prompt whose turn was streaming in 7 runs of 8, which is OW-zedawo again (bun 1.4.0, Emacs 31.1, measured 2026-09-29; `docs/MANUAL_TESTING.md`, OW-hiliti).
Until ark3/agentpane#73 the helper wrote no reply at all for a request its own teardown aborts (`runHelper` in `src/emacs/helper.ts`), since the abort says nothing of whether the request reached the backend; what that silence still decided was the echo area, which then named the helper's exit rather than the abort.
A request made through a helper that has exited, before its teardown, is sent nowhere: until ark3/agentpane#73 it ran its reached-no-backend path at once, quietly, so a prompt's watch is abandoned before the teardown could end it as a turn from elsewhere, and is recorded for the teardown to answer as the death with its failure path and one echo-area line, rather than refused with an error that signalled out of the jsonrpc.el timer running the handler that chained it.
The answers ran one tick after the teardown, so the in-flight flags stay set that tick longer, and a reply jsonrpc.el held back behind a synchronous request is still the answer: as of jsonrpc.el 1.0.29 on Emacs 31.1, measured 2026-09-28, it is handed on from a timer queued as the synchronous request unwinds, after the teardown's timer and before the answers'.
